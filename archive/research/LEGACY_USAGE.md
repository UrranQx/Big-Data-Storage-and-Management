# Speedrun.com ETL

Текущие сборщики — исследовательский прототип. Успешные проверки отдельных игр
не означают, что источник полностью изучен или готов универсальный ETL для ЛР1.
[DATA_MODEL.md](DATA_MODEL.md) — черновик ER-модели, ключей, полей и справочников
ID → название; ODS и будущая DDS разделены, открытые вопросы перечислены явно.
Модель — только набросок: перед использованием в реализации её необходимо
обсудить с пользователем и получить его явное утверждение.

Документы планируют весь семестр: ЛР1 — сбор и ODS в трёх хранилищах,
Airflow и сравнительные замеры; ЛР2 — нормализация DDS, SCD, Data Quality
и вычисление PB/WR; ЛР3 — витрины, Superset и OpenMetadata.
Подробные границы этапов указаны в начале [DATA_MODEL.md](DATA_MODEL.md).

[SOURCE_CONTRACT.md](SOURCE_CONTRACT.md) — общий контракт сбора для разных игр,
покрытие API, история наблюдений и модель интервалов PB/WR для лабораторных работ.

## Текущее решение о сборе (2026-10-10)

Основной источник ранов — публичный лидерборд v2. После Portal пользователь выбрал
**Minecraft: Java Edition (`mc`)** для следующей полной выгрузки:
все статусы, `obsolete=1`, включая архивные
категории полной игры; без level runs и отдельной Category Extensions.
`orphaned` сохраняем как признак и исключаем из общей статистики. Исходные
данные не удаляем; автор подачи (`submittedById`) хранится отдельно от игроков.
V1-добор — только опциональный аудит, такие записи не входят в статистику v2.

Краткие результаты сессии, пути к данным и ограничения API находятся в начале
[COLLECTION_PLAN.md](COLLECTION_PLAN.md). Новые сборы — 20 запросов/мин:
60 запросов/мин получили HTTP 429. Агентов не используем. После каждой
выгрузки останавливаемся для просмотра пользователем.

## Каталог всех игр — отдельный первый этап

```powershell
python collect_games.py --output data/games_catalog_20261010 --rpm 20
python -m unittest test_collect_games -v
```

Сборщик читает все страницы публичного `GetGameList` API v2 в порядке названий,
без фильтрации типов игры. Проверяет номера и размеры страниц, постоянство
заявленного количества и уникальность ID, включая страницы за пределами 10 000
записей. По умолчанию лимит — 20 запросов/мин; исходные ответы кэшируются для продолжения
сбора в той же папке. Для нового снимка нужна другая папка `--output`.

Результат: `processed/games.csv` (UTF-8 с BOM), `games.sqlite`, `games.jsonl`,
`platforms.json`, исходные ответы `raw/` и `manifest.json`. Каталог публичный,
удалённые и закрытые записи не входят в область полноты; страницы получаются
последовательно во времени, снимок не атомарный.

`site_run_count` сохраняет исходный счётчик сайта `runCount`. Это не проверенное
число полных забегов во всех статусах. Топ-10 и выгрузка забегов относятся к
следующим этапам и этим скриптом не запускаются.

## Два топ-10 — второй этап

```powershell
python rank_games_two_metrics.py --output data/games_ranking_20261010
```

Рейтинг сайта использует `GetGameList` с `orderType=8` и сохраняет порядок API.
Второй рейтинг использует статистику `GetGameSummary.stats.totalRunsFG`;
Category Extensions исключаются по `gametypes` v1. Проверяются кандидаты
за пределами первого топ-10, пока следующий общий счётчик каталога не станет
строго меньше десятого счётчика полных забегов. Граница поиска и исходные
счётчики сохраняются в `two_metrics_manifest.json`.

Результат: `top10_site.csv`, `top10_full_game_verified.csv`,
`full_game_candidates.csv` и `two_metrics.md`. Это рейтинг по статистике сайта,
а не независимый пересчёт каждого рана каждой игры; снимок не атомарный.
Сверка Super Mario Odyssey обнаружила расхождение: `totalRunsFG=23502`,
сумма пагинации подтверждённых ранов по полным категориям с `obsolete=1` — 23499.
Причина установлена: три подтверждённых Any% без участников (`players=[]`)
учитываются статистикой игры и доступны в v1, но отсутствуют в лидерборде v2.
Карточки v2 помечают их `orphaned=true`, `issues=["no players"]`.
Полный пересчёт v1 дал 23502, подтвердив статистику сайта для этого снимка.
Доказательства: `data/smo_stats_audit_20261010/REPORT.md` и `report.json`.
Диагностика: `audit_smo_stats.py`, `audit_smo_any.py`, `audit_smo_proof.py`.
Полная выгрузка
забегов игры на десятом месте не запускается этим скриптом.

## Выгрузка Minecraft: Java Edition

```powershell
python collect_all.py --game mc --output data/minecraft_java_20261010 --rpm 20 --workers 4
python validate.py --output data/minecraft_java_20261010
```

Политика сбора совпадает с Portal: 11 категорий полной игры, включая две
архивные, все статусы и obsolete; без level runs и отдельной Category Extensions.
API повторяет большой список игроков на каждой странице; четыре HTTP-потока
используют общий ограничитель 20 запросов/мин. При возобновлении используются
ответы из `raw/`; для обновления данных нужна новая папка снимка.

Результат: **46 170 ранов** — 29 373 verified, 16 571 rejected, 226 new;
20 837 obsolete, 19 169 профилей участников (14 721 с географией).
Все проверки `validate.py` прошли; 260 страниц verified Any% Glitchless
дали ровно 25 945 уникальных ID, включая страницы за пределами 10 000.
Таймер verified: 29 340 IGT и 33 RTA; сравнивать их отдельно.
Статистика сайта до/после сбора: 30 137 full-game verified, разница с v2 — 764.
Численная причина установлена: архивная Combined Any% Glitchless содержит
764 verified-записи в общем списке v1 и ноль в лидерборде v2:
29 373 + 764 = 30 137. Её записи суммируют PB в разных диапазонах версий,
обновлялись ботом. В пяти проверенных карточках v2 `orphaned=true`, хотя
игроки известны. Orphaned не обязательно означает отсутствие игрока.
Восстановлены 745 уникальных архивных ID; точное количество 764 независимо
проверено на границах блока категорий. Внутренний SQL статистики недоступен.
`znk937lz` — отдельный orphaned в Any%; его наличие в v1 не доказывает учёт
в `/stats`, прежнее вычитание одного из разницы исправлено.
Отчёт: `data/minecraft_java_stats_audit_20261010/REPORT.md`.

## Все забеги Celeste

```powershell
python collect_all.py --game celeste --output data/celeste --rpm 20 --audit-v1
python validate.py --output data/celeste
```

`collect_all.py` использует публичный API v2 сайта (`GetGameData`,
`GetGameLeaderboard2`), поскольку у v1 `/runs` смещение 10 000 возвращает HTTP 400.
На Celeste подтверждено, что разбиения Any% по платформе и статусу недостаточно:
у PC verified есть разрыв между первыми и последними 10 000.
У v2 проверена страница 101; сбор идёт по всем страницам из `pagination.pages`.
Это API веб-интерфейса без обещания стабильности, его схема может измениться.
По умолчанию два HTTP-соединения используются одновременно; общий потокобезопасный
ограничитель разрешает начинать не более 20 запросов/мин. Это обычная загрузка
страниц в одном процессе Python; дополнительные агенты не используются.

## Выгрузка Portal по принятой политике v2

```powershell
python collect_all.py --game portal --output data/portal_20261010 --rpm 20 --workers 2
python validate.py --output data/portal_20261010
```

`--audit-v1` по умолчанию выключен. В `runs` хранятся поля `submitted_by_id`,
`orphaned`, `issues_json`, `statistics_eligible`, `source_api`. Основные
аналитические представления SQLite: `runs_for_statistics` (все статусы)
и `verified_runs_for_statistics` (только подтверждённые). Оба исключают
orphaned и записи, добавленные опциональным v1-аудитом; для них также есть CSV.
`runs.csv` сохраняет все полученные записи для аудита, `raw/` — исходные ответы.
В `players` сохраняются `area_id` и `country_code` из географии профиля.

Результат Portal: **20 134 рана** (16 620 verified, 3 425 rejected, 89 new),
5 категорий, 6 102 участника; все проверки `validate.py` прошли.
У 1 621 verified-забега задан только таймер с загрузками: `primary_time_source`
показывает, из какого поля взято `primary_seconds`; отсутствующее время без
загрузок остаётся NULL. Для сравнения времён разделять таймеры и подкатегории.
Статистика сайта FG=16 622; набор v2 содержит 16 620 подтверждённых записей,
причина разницы подтверждена: `znrek39y` (Inbounds) и `y8r6rg5m`
(Inbounds Legacy) — orphaned, без участников. Они исключены согласно политике.
Доказательства: `data/portal_stats_audit_20261010/REPORT.md`.

Включаются все открытые категории полной основной игры, **в том числе архивные**,
статусы `verified`, `new`, `rejected`, прежние результаты игроков (`obsolete=1`),
забеги без видео (`video=0`) и эмулированные (`emulator=1`). `values=[]` не задаёт
фильтр версии или подкатегории. Level runs и другие игры, включая Category Extensions,
не включаются. Удалённые/приватные записи API вернуть не может.

В каждой категории/статусе проверяются полученные уникальные ID против
`pagination.count`, номер страницы, фильтры и отсутствие повторений.
Если число записей меняется во время сбора, выгрузка помечается `incomplete`.
Дополнительно v1/v2 сверяются по полным наборам ID там, где v1 допускает это.
**На Celeste выявлено, что v2 пропускает отдельные старые забеги без игроков.**
Они добавляются из v1; исходная запись сохраняется внутри `raw_json`, а
`source_api=v1` позволяет отличить дополнения. Для таких записей признак `obsolete`
неизвестен и остаётся NULL, поскольку v1 его не возвращает.
Большая Any% в v1 дополнительно собирается отдельными запросами по каждому
проверяющему, обнаруженному в v2 и выборках начала/конца/смещения 9 800 v1.
Каждый такой список проходится полностью, без превышения смещения 10 000.
Также полностью читаются первые и последние доступные 10 000 verified-записей
Any% в v1. Недоступные фильтры удалённых проверяющих (HTTP 404) отмечаются в отчёте.
Число дополнений и результаты сверки сохраняются в манифесте.

Это не математическое доказательство полноты всей базы: неизвестный проверяющий,
представленный только пропущенными v2 записями в недоступной середине v1, может
остаться необнаруженным. Поэтому `status=complete` означает завершение процесса,
а `coverage_status=not_independently_proven_exhaustive` обозначает ограничение
проверки полноты. Не следует называть выгрузку гарантированно 100% полной.
Снимок не транзакционный, время получения сохраняется.

Результаты находятся в отдельной папке `data/celeste`, пилот сохраняется.
Схема `runs` дополнена статусом, признаком obsolete, проверяющим, причиной отклонения,
комментарием и исходным `raw_json`. Метаданные версий/подкатегорий находятся в
`variables` и `variable_values`, платформ и игроков — в отдельных таблицах.
`date` для v2 содержит полный `performedAt` ISO timestamp. Отсутствующее время
отклонённого/ожидающего забега остаётся NULL. Исходные ответы сохраняются в `raw`.
Доступный для диагностики список полей может отличаться от v1; это отражено в схеме.
`manifest.json` содержит состояние сбора, счётчики и результаты сверки.

```powershell
python -m unittest -v test_collect test_collect_all
```

Python 3.11+, без сторонних зависимостей. Запуск из PowerShell:

```powershell
python collect.py
# Другой набор игр:
python collect.py --games portal portal_2 --rpm 60 --top-categories 2
```

Ключ берётся из `SPEEDRUNCOM_API_KEY`; в файлы и логи не записывается.
Используются только GET-запросы. Лимит API: 100 запросов/мин на IP;
сборщик ограничен 60 запросами/мин, страницы по 200 строк.
Ошибки 420/429 вызывают ожидание минимум 65 секунд; временные ошибки повторяются.
Другие клиенты с того же IP также расходуют лимит.

## Extract

Пилот по умолчанию: Portal, Portal 2, Super Metroid, Undertale, Hollow Knight.
Это целевая выборка известных игр, а не рейтинг популярности всех игр сайта.
Для каждой категории полной игры читаются все страницы подтверждённых забегов, включая старые
результаты одного игрока. Забеги отдельных уровней не собираются. При ограничении
смещения 10 000 категория разбивается по платформам. Если даже такой список превышает
лимит, сбор останавливается с ошибкой и не объявляет неполную выгрузку завершённой.
Ответы с URL и временем получения хранятся в `data/raw`.
Повторный запуск использует кэш и продолжает незавершённый сбор.
Для нового снимка используйте отдельную папку `--output data/snapshot_YYYYMMDD`.
API меняется во время пагинации: это не транзакционный снимок, возможны пропуски
при параллельных изменениях источника; повторяющиеся ID устраняются.

## Transform

Считается количество уникальных verified-забегов полной игры в каждой категории.
Выбираются все категории с `any%` / `any percent` в имени и две самые массовые
категории типа `per-game` (включая miscellaneous). При равенстве — порядок ID.
Подкатегории/версии сохраняются в `values_json`; они не смешиваются при хранении,
но количество для выбора считается на уровне основной категории.
Any% не переименовывается в других играх автоматически: например, Any% Glitchless
тоже включается, а название вроде Any Ending без процента не считается any%.

## Load

`data/processed`: CSV (UTF-8) и SQLite с таблицами `games`, `categories`, `runs`,
`run_players`. `categories` содержит все категории и признак выбора, число забегов
и причину. В `runs` — только выбранные категории и полные verified-забеги.
Время — секунды; даты и неизвестные значения сохраняются без подстановок.
`data/manifest.json` содержит итоговый объём и статус завершения.
Проверяются уникальность ID, связи забегов с категориями и неотрицательное время.
