Планируем три логически разных ETL-процесса из одного источника — Speedrun.com:
метаданные игр, забеги и профили участников. В ЛР1 сохраняем исходные данные
в ODS. Нормализация DDS, SCD, отдельный DAG Data Quality и вычисление PB/WR
относятся к ЛР2; аналитические витрины, Superset и OpenMetadata — к ЛР3.
Утверждены PostgreSQL, MongoDB и Garage.

Уточнение перед ЛР1: ниже логические шаги, а не требование сделать каждый шаг
отдельной задачей Airflow. Для первого варианта достаточно последовательного
сбора, raw + manifest и простых загрузчиков. Последнее уточнение пользователя:
целевой охват глобальный; одна игра служит только проверкой перед обходом
каталога. Профили можно выделять из встроенных
списков API, если полей достаточно; отдельный запрос на каждого игрока не нужен
сам по себе. Возобновление после сбоя может повторять раздел целиком,
но должно сохранять общий прогресс обхода. Старые выгрузки не заменяют свежий ETL.

## 1. `games_metadata` — игры и их метаданные

```text
Начать снимок
    ↓
Получить все страницы каталога игр
    ↓
Проверить пагинацию и уникальность ID
    ↓
Получить категории, переменные, значения и платформы выбранных игр
    ↓
Подготовить пакет исходных данных
    ├→ Загрузить в хранилище №1
    ├→ Загрузить в хранилище №2
    └→ Загрузить в хранилище №3
    ↓
Проверить загрузки и завершить снимок
```

Результат: исходные ответы, сведения **ID → название**, параметры запросов
и сведения о покрытии. Итоговый процесс обходит каталог, а список игр позволяет
ограничить проверочный прогон. Такие справочники в ODS не требуют реализации всей
нормализованной DDS-модели.

Сейчас есть исследовательские скрипты получения каталога и метаданных.
Airflow DAG и загрузчики в три выбранных хранилища ещё не реализованы.

## 2. `runs` — забеги выбранных игр

```text
Дождаться готовых метаданных
    ↓
Сформировать разделы: игра × полная категория × статус
    ↓
Получить все страницы каждого раздела, включая obsolete
    ↓
Проверить страницы, уникальные ID и заявленные количества
    ↓
Сохранить исходные ответы и диагностику покрытия
    ├→ Загрузить в хранилище №1
    ├→ Загрузить в хранилище №2
    └→ Загрузить в хранилище №3
    ↓
Проверить загрузки и завершить снимок
```

Результат: verified, rejected и new, включая прежние результаты игроков.
Orphaned сохраняем с признаком. Level runs и отдельные Category Extensions
в основную область сбора не включаем. **PB/WR здесь не рассчитываем.**

Счётчики сайта до и после сбора можно сохранить дополнительными задачами
этого DAG. Успешное выполнение не означает доказанную полноту всей базы сайта:
ограничения API и непроверенные разделы фиксируем в диагностике покрытия.

Сейчас есть пробные выгрузки Portal и Minecraft и проверки отдельных случаев.
Оркестрацию, загрузчики ODS и поведение обновлений ещё предстоит реализовать
и проверить; универсальная полнота сборщика не доказана.

## 3. `players` — профили участников

```text
Дождаться готовой выгрузки забегов
    ↓
Извлечь уникальные ID всех зарегистрированных участников
    ↓
Выделить встроенные профили; при нехватке полей получить отдельно
    ↓
Зафиксировать полученные и недоступные профили
    ↓
Подготовить пакет исходных данных
    ├→ Загрузить в хранилище №1
    ├→ Загрузить в хранилище №2
    └→ Загрузить в хранилище №3
    ↓
Проверить загрузки и завершить снимок
```

Результат: исходные профили, имена, страны и время наблюдения. Участников
берём **из всех собранных статусов**, а не только с лидерборда. Гостей без ID
сохраняем в данных забега; отсутствие страны допустимо. Автор подачи и
проверяющий не считаются участниками без явной связи в исходных данных.

При повторном сборе сохраняем наблюдения и изменившиеся исходные состояния,
без полной копии неизменного профиля на каждый запуск. SCD и анализ стран
оставляем для ЛР2–ЛР3. Те же правила истории применяются к другим сущностям.

Сейчас данные игроков получены из списков профилей, встроенных в ответы API.
Отдельный сборщик публичных профилей, Airflow DAG и загрузчики ещё предстоит
сделать; поведение API для недоступных профилей требует проверки.

## Общие правила

- Зависимости: метаданные → забеги → профили участников. Связываем конкретные
  снимки и область сбора; успешность произвольного прошлого запуска недостаточна.
- Общий ограничитель — 20 запросов в минуту на весь проект. В Airflow его
  необходимо реализовать для всех процессов; нынешний ограничитель внутри
  одного процесса Python сам по себе этого не обеспечивает.
- Повторные попытки учитывают HTTP 429 и Retry-After; параметры запросов,
  исходные ответы, ошибки и время получения сохраняем без секретов.
- Предусматриваем продолжение после сбоя и повторную загрузку того же пакета
  без дубликатов. Свежая проверка может сохранить небольшую отметку наблюдения,
  но не требует ещё одной копии неизменных данных. Изменившееся исходное состояние
  сохраняем вместе с прежним; retry того же наблюдения не создаёт новое.
  Подробности — «История без дублей» в `SOURCE_CONTRACT.md`. «Снимок» в схемах
  означает логический набор данных, не обязательную полную физическую копию.
- Один полученный пакет загружаем в три хранилища. Это позволяет сравнивать
  сервисы на одинаковых данных и не увеличивать нагрузку на API повторным сбором.
- Завершение снимка зависит от результатов всех трёх загрузок. Ошибки и
  частичное покрытие должны быть видны, а не скрыты общим статусом успеха.
- Проверки ЛР1 контролируют сбор и загрузку. Они не заменяют отдельный
  DAG Data Quality для преобразованного DDS в ЛР2.

Схемы показывают логические шаги. Точное разбиение на задачи Airflow,
параллелизм, расписания и механизм зависимостей определим при реализации
после утверждения плана.
