## Область сбора

Для каждой доступной игры: все доступные категории полной игры, включая архивные;
все доступные забеги со статусами new, verified, rejected; прежние результаты
игроков; правила, переменные подкатегорий, платформы, участники, история WR сайта
и снимки Speedrun stats. Level runs и challenges в основной датасет не включаются.
Отдельные игры Category Extensions требуют явного решения о включении в каталог.

## Извлечение

1. Получить каталог игр, объединить доступные списки v1/v2 по game_id, сохранить
   все страницы и сведения о покрытии. Не останавливаться на первой странице.
2. Получить категории и переменные из v1/v2, включая архивные метаданные v2.
3. Читать все страницы категории отдельно по каждому статусу, с obsolete=1,
   video=0, emulator=1, без фильтра версии/подкатегории.
4. Дедупликация строго по run_id. Несколько забегов одного игрока являются
   разными фактами. У забега может быть несколько участников или ни одного.
5. При явном включении v1-аудита: сверка v1/v2 и архивирование записей,
   отсутствующих в основном списке, отдельно от основной статистики. Запросы по
   игрокам/гостям могут дополнять и проверять архив, но список текущих рекордсменов
   не является полным каталогом участников, особенно для rejected-only игроков.
6. Если v1 достигает смещения 10 000: сохранять доступные обе половины и
   использовать доступные разбиения. Не обозначать закрытую пагинацию частичной
   выборки как доказательство полноты всей категории.
7. Хранить evidence: параметры, timestamps, число страниц, ожидаемые и фактические
   количества, доступность фильтров и расхождения ID. Непроверенное покрытие
   отмечать отдельно от технически успешного выполнения процесса.

## История WR

Сохранять исходный ответ публичного GetGameRecordHistory как независимый продукт
источника, вместе с параметрами зачёта. Внутри recordEventList события могут
содержать несколько runList, поэтому число событий не обязательно равно числу ID.
В ЛР2 WR считать дополнительно из собранных verified-забегов, включая прежние результаты.

Зачёт определяется игрой, категорией и релевантными подкатегориями/фильтрами,
таймером и направлением сравнения. Все версии игры не следует автоматически
разделять на разные зачёты: необходимо учитывать правила категорий и переменных.
Равные времена и неопределённые даты обрабатывать явно.

Различать историю по дате выполнения, отправки и подтверждения. Текущее состояние
API не восстанавливает достоверно прежний статус забега, который позже отклонили.
Для будущих изменений сохранять историю состояний с временем наблюдения.

## Speedrun stats

Сохранять timestamped снимки исходных stats/GameStats из GetGameSummary для каждой
игры до и после сбора (ЛР1). Для диагностики сбора записывать расхождения
счётчиков, время снимков и состояние покрытия. Собственные формулы показателей
подготовить в ЛР2; систематическое аналитическое сравнение метрик — в ЛР3.

Первичная проверка Celeste (2026-10-03):

- сайт totalRunsFG: 27 330;
- локальные verified-забеги полной игры: 27 330;
- все локальные статусы: 31 373 (27 330 verified, 4 042 rejected, 1 new);
- сайт totalRuns: 52 248 = 27 330 FG + 24 918 IL + 0 challenges;
- публичный GetGameRecordHistory для Any% вернул 121 событие.

Совпадение FG с verified является наблюдением для одного снимка, а не доказанной
универсальной формулой сайта или независимым доказательством полноты всех ID.
Свежие исходные ответы: data/celeste/research/raw; удобные копии:
site_stats.json и site_wr_history_any.json.

Для totalPlayers, activePlayers, totalRunTime и recentRuns необходимо установить
область подсчёта, статус, временное окно и выбранный таймер. Общие метрики игры
могут учитывать IL; архив только полной игры не даёт независимого расчёта всех
метрик страницы. Расхождение может возникать из-за определения метрики, кэша,
разных моментов наблюдения, неполной выгрузки или ошибки сайта.

## Игроки и география

Для каждого зарегистрированного участника хранить публичные профильные атрибуты:
user_id, отображаемое имя, страну/регион профиля, ссылку и время наблюдения.
В ЛР1 сохранять исходные профильные данные каждого снимка; историю изменения
атрибутов в виде SCD2 формировать в DDS в ЛР2.
Связь run_players остаётся отдельной: один забег может иметь несколько участников.
Гостевых игроков, удалённые профили и отсутствие страны не заменять вымышленной
страной и не выводить страну по имени, языку комментария или IP.

Флаг/страна профиля — заявленная пользователем география, а не подтверждённое
гражданство. Текущую страну не считать известной страной на дату старого забега.
Для исторических расчётов указывать: текущая география или география, наблюдавшаяся
на соответствующую дату. До начала наблюдения историю изменения страны восстановить
полностью нельзя.

Будущая аналитика ЛР3 (на основе DDS ЛР2). Карточка игры и категории:
уникальные verified-участники по стране, их доли,
доли мест в top-N по личным лучшим результатам, текущие WR и длительность
наблюдаемого/реконструируемого владения WR. Прежние результаты сохраняются в архиве,
но при анализе текущей силы игрока не дают ему дополнительные места в топе.
Совместные результаты учитывать по отдельной явно указанной методике: команда
как единица либо долевой вклад участников. Не суммировать страны без учёта того,
что один коллективный результат может представлять несколько стран.

Для сравнения мастерства использовать позиции/перцентили внутри сопоставимых
зачётов (категория, релевантные подкатегории, платформа и правила), а не среднее
время по разным категориям. В отчётах показывать объём выборки, долю неизвестных
стран и дату профилей. Массовость участия, количество отправок и доминирование
на верхних местах являются разными метриками.

Карточка игрока: игры/категории, история результатов и личных рекордов, места,
WR и срок владения ими; новые результаты добавляются, прежние не удаляются.

## Обновления

Новые submissions читать по времени отправки с перекрытием и upsert по run_id.
Изменения статусов: повторная проверка pending и потока недавно подтверждённых.
Старые результаты/правила/WR перепроверять по расписанию. Хранить исходные снимки
и историю обнаруженных изменений, включая исчезновение ранее известной записи;
один HTTP 404 не считать достаточным доказательством удаления.
Существующий бессрочный кэш сборщика предназначен для возобновления первоначальной
выгрузки. Для обновлений нужны новые снимки или управляемая актуализация кэша.

## Ограничения

v1 обрывает /runs на смещении 10 000. v2 может пропускать исторические записи без
игроков; на Celeste одна такая запись восстановлена из v1. Фильтры удалённых
проверяющих возвращают 404. Удалённые/закрытые записи и скрытые категории нельзя
гарантированно восстановить через доступные публичные списки.
