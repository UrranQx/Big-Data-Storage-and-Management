# Инструкции для агентов

## Задача и границы

- Общаться с пользователем по-русски. Работать одним агентом: не создавать
  субагентов и не делегировать задания другим агентам.
- Источник требований — `Лабораторные_работы_Технологии_хранения_больших_данных_-1.md`.
  Текущий этап — подготовка и выполнение только ЛР1, а не всего семестра сразу.
- Пользовательский сайт не требуется ни в одной лабораторной. Не реализовывать
  сайт, собственный frontend/backend, аккаунты, уведомления, рекомендации,
  эмбеддинги или интеграции Twitch/YouTube без отдельного запроса пользователя.
  `ANALYTICS_IDEAS.md` — идеи на будущее, не список обязательных задач.
- ЛР1: Airflow в Docker Compose, три различных сервиса хранения, минимум три
  логически различных ETL DAG, сбор сырых данных в ODS, сравнительные замеры,
  обоснованный выбор хранилища и отчёт с демонстрацией.
- ЛР2: DDS, нормализация, очистка, SCD, отдельный DAG Data Quality и зависимости
  ODS → DDS. ЛР3: витрины, их DAG, Superset и OpenMetadata. Для них сейчас
  достаточно места в структуре репозитория; не разворачивать их заранее.
- Не добавлять Kafka, Kubernetes, dbt, отдельный сервис API или другую
  инфраструктуру без конкретной необходимости по заданию и согласованному плану.

## Минимально достаточная реализация ЛР1

- Передача коллеге: актуальный переносимый запуск — `speedrun_etl.batch`
  (`--top 10` или `--all`), без исходных данных автора. Инструкция в
  `docs/TEAM_HANDOFF.md`. Старые queue_driver/benchmark/fresh_cycle не являются
  стартовой командой коллеги. Не запускать локальный top-10 автоматически
  вместо подготовки передачи. Полный свежий Minecraft и smoke-проверку
  поднабора различать; успешный smoke не доказывает полный e2e.
- Актуальное уточнение пользователя 2026-10-16: основные сущности ODS —
  **игры (полные карточки), раны каждой игры, игроки (полные профили)**.
  Связи строить по ID: ран относится к игре и одному или нескольким участникам;
  игрок может участвовать в разных играх. Это предметные наборы для трёх DAG,
  а не требование ограничиться несколькими столбцами или заранее строить DDS.
  Сохранять все исходные поля, различающиеся состояния и происхождение.
  Повторное появление неизменного профиля на странице не требует отдельного
  документа/строки/объекта. Метаданные запросов и покрытия — вспомогательные.
  Прежняя реализация payloads/responses/observations/manifests пересматривается;
  прототип grouped-v2 не утверждён как замена. Точная новая физическая схема
  ещё не выбрана. Основное описание — актуальное начало `DATA_MODEL.md`.
- Последующее разрешение пользователя 2026-10-16: после успешной проверки
  Half-Life во всех трёх ODS удалить данные стенда, включая Docker volumes,
  и заново выполнять запросы. Условие проверено; шесть volumes только проекта
  speedrun-lab1 удалены и созданы заново, исходники/архив data.zip/секреты/отчёты
  сохранены. Запущен свежий Half-Life на entity-v2, далее каталог и Minecraft.
  Старые загрузки и top-5 автоматически не возобновлять. Новые данные не
  удалять снова без необходимости; переупаковку не выдавать за свежий HTTP-сбор.
- Целевой охват — глобальный каталог и доступные данные по всем играм в
  согласованной области, не одна демонстрационная игра. Собирать заново через
  итоговый ETL; старые профили и raw не использовать для обхода реального сбора.
  Одна игра — проверочный этап, не окончательное ограничение продукта ЛР1.
  Оценить бюджет запросов, время и объём; не обещать полноту всей базы сайта.
- Начинать с последовательного сетевого сбора и простого ограничения частоты.
  Параллельность и распределённый ограничитель не нужны сами по себе. Выбранный
  способ исполнения должен исключать одновременные запросы разных сборщиков
  сверх общего бюджета; один pool без pacing запросов этого не гарантирует.
- Для ODS достаточно исходных ответов и небольшого манифеста с ID снимка,
  параметрами, временем, счётчиками и ошибками. Описанные в черновиках таблицы
  наблюдений и запросов — варианты, а не обязательная схема из множества таблиц.
  Это не предписывает файловую модель и не отменяет сохранение истории:
  полные исходные поля и изменившиеся состояния нужны уже в ЛР1 для будущих
  исследований, не только PB/WR. Повторы не размножают сущности и payload;
  свежая проверка отличается от retry. Нельзя просто затирать прошлое состояние.
  Требования и границы — раздел «История без дублей» в `SOURCE_CONTRACT.md`.
- Для DAG игроков использовать достаточные публичные данные профилей из API,
  в том числе встроенные в ответы. Отдельный endpoint и запрос на каждого
  пользователя нужны лишь при реальной нехватке требуемых полей. DAG должен
  иметь собственный логический результат, а не быть третьей копией загрузки ранов.
- Для глобального сбора нужны сохранение прогресса по играм/разделам и продолжение
  после сбоя. Не начинать весь обход заново и не перечитывать весь сайт при
  каждом обновлении. Глубину контрольных точек и стратегию обновления выбрать
  по фактическому объёму, без универсальной платформы CDC.
- Сравнение хранилищ — небольшой воспроизводимый эксперимент: одинаковые данные,
  время загрузки, объём и простое чтение, где применимо. Не строить отдельный
  benchmark-фреймворк, не добавлять SQL-движок для объектного хранилища.
- Проверенные функции прототипов разрешено переносить с минимальными изменениями.
  Не переписывать всё ради новой архитектуры. Достаточно функций и конкретных
  загрузчиков; универсальные классы/плагины и дополнительные уровни абстракции
  вводить только при подтверждённой необходимости.
- Согласовать стек, ODS и область один раз. После утверждения не запрашивать
  согласование каждого файла или технической мелочи. Сохранить запрошенную
  пользователем остановку после первого небольшого e2e перед полной выгрузкой.

## С чего начать

1. Прочитать задание, `docs/HANDOFF.md`, `docs/REPOSITORY_STRUCTURE.md`.
2. Прочитать `DAGs.md`, ODS и границы этапов в `DATA_MODEL.md`,
   `SOURCE_CONTRACT.md` и результаты `COLLECTION_PLAN.md`.
3. Проверить реальные файлы и окружение; не считать сведения прошлой сессии
   текущим состоянием сервисов или источника.

Стек PostgreSQL/MongoDB/Garage и Airflow уже утверждён и реализован; повторно
его не выбирать. Предыдущая физическая модель ODS реализована, но пользователь
попросил пересмотреть её в пользу перечисленных выше предметных сущностей.
Исторические разделы `DATA_MODEL.md`, `DAGs.md` и плана не отменяют это уточнение.
Новая entity-v2 упаковка и пакетные загрузчики реализованы и проверены;
фактическое состояние и границы разрешённого сброса указаны выше и в HANDOFF.
Защита темы и таблица источников не требуют действий: пользователь попросил
ими не заниматься.

## Архив и данные

- `archive/` — отстойник исследовательских прототипов, не рабочий код ЛР1.
  Читать для изучения конкретного случая можно. Не импортировать оттуда в новый
  код, не подключать архив к Airflow и не включать его в рабочие образы.
- Не запускать архивные скрипты массово и не импортировать исследовательские
  модули ради знакомства: часть выполняет сетевые запросы при импорте.
  Порядок безопасного запуска описан в `archive/research/README.md`.
- Полезные решения переносить в `src/speedrun_etl/` осознанно после проверки.
  Архивные тесты подтверждают лишь поведение прототипа, не готовность ЛР1.
- `data/` содержит локальные исходные ответы, SQLite/CSV и результаты прошлых
  сборов. Не включать в Git или Docker context. Пользователь рассматривает
  очистку и сбор с нуля; точный состав удаления пока не утверждён. До уточнения
  не удалять и не перезаписывать. Новый итоговый ETL начинает свежий сбор без
  использования экспериментального кэша; это не требование полной копии всех
  данных на каждый запуск. Важные небольшие отчёты скопированы в
  `docs/research/evidence/`, но полные данные там не продублированы.
- Старые команды `python collect_all.py ...` в исторических документах относятся
  к прежнему расположению файлов. Инструкции адаптации — в README архива.

## Правила источника и ETL

- Полные категории основной игры, включая доступные архивные; статусы new,
  verified, rejected; старые результаты (`obsolete=1`). Level runs и отдельные
  Category Extensions исключены из основной области ранов. Каталог игр шире.
- Основной источник — публичный API v2 сайта. V1 — опциональная сверка/добор,
  со своим происхождением, без незаметного смешивания аналитических выборок.
- Orphaned не удалять из ODS, сохранять исходный признак; исключение из общей
  аналитики — отдельная политика. Orphaned не всегда означает отсутствие игроков.
  Участник, автор подачи и проверяющий — разные роли.
- Сохранять raw, параметры и время запросов, доступные даты событий, все таймеры,
  ID и названия справочников, диагностику покрытия. Неизвестное не выдумывать.
- Не объявлять доказанной полноту всего сайта. Ограничения и расхождения
  фиксировать отдельно от технического успеха запуска. Совпадение со stats
  не доказывает формулу сайта или полноту уникальных ID.
- Для новых запросов исходный консервативный бюджет — 20 запросов/мин суммарно
  на весь проект, включая повторы и параллельные задачи. Это наше ограничение,
  не обещанный лимит сервиса. Учитывать 429/Retry-After. Внутрипроцессный lock
  старого клиента не является общим ограничителем для задач Airflow.
- Избегать передачи больших JSON через XCom; использовать ссылки на артефакты
  и небольшие манифесты. Одни извлечённые данные загружать в три хранилища,
  обеспечивая сравнимость и повторяемость загрузок.
- Проверки пагинации, покрытия, загрузки и отсутствия дублей при повторе нужны
  уже в ЛР1. Они не означают реализацию всего DDS Data Quality из ЛР2.

## Секреты, проверки и Git

- `SPEEDRUNCOM_API_KEY` уже использовался из переменной окружения; проверить
  наличие без вывода значения, только если это нужно задаче. Не записывать ключи
  в Git, URL, логи, отчёты, манифесты или команды. Не передавать ключ v1 в v2.
- `.env` и локальные подключения исключены из Git. Допустим `.env.example`
  только с безопасными заглушками. Не использовать реальные секреты в тестах.
- Внешние массовые сборы не запускать на этапе планирования. Для реализации
  согласовать небольшую область демонстрации; новые большие выгрузки выполнять
  поэтапно с просмотром результата пользователем.
- Проверять версии и совместимость инструментов по официальной документации
  при планировании реализации. Не считать прежний Docker Engine запущенным.
- Проверять существенное поведение: повторы, сбои загрузок, границы пагинации,
  одинаковый логический снимок в хранилищах. Не создавать тесты ради количества.
- Не заявлять запущенные сервисы, успешный сбор или замеры без фактической
  проверки. Различать факт, гипотезу, план и ограничение окружения.
- Перед Git-операциями проверить состав файлов и исключения. GitHub-репозиторий,
  публикация и push не выполняются без соответствующего запроса пользователя.
