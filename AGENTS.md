## Контракт источника и ETL

- Основные сущности: полные карточки игр, раны, полные публичные профили игроков;
  связи по ID, один ран может иметь нескольких участников. WR — отдельный DAG.
- Сохранять все исходные поля, различающиеся состояния, raw, параметры/время
  запросов, даты событий, таймеры, справочники, происхождение и coverage.
  Неизменные профили/payload не размножать; прошлые состояния не затирать.
  Повторная упаковка не является свежим HTTP-сбором. См. SOURCE_CONTRACT.md.
- Основной источник — публичный v2. V1 — только явная опциональная сверка/добор
  с собственным происхождением, без смешивания выборок и передачи ключа v1 в v2.
- Область ранов: full-game категории основной игры, доступные архивные,
  new/verified/rejected, obsolete=1. Level runs и Category Extensions исключены.
  Каталог шире. Orphaned сохранять; аналитическое исключение — отдельная политика.
  Участник, автор подачи, проверяющий — разные роли.
- Полноту сайта и формулу stats не объявлять доказанными. Ограничения источника
  отличаются от технического успеха DAG; smoke не доказывает полный e2e.
- Одна известная игра требует только её GetGameData; каталог один на очередь.
  Порядок популярности — свежий каталог, runCount DESC, ID ASC при равенстве.
  Standard — по умолчанию, разрезы дат только по явному --accelerate-dates.
- Все запросы, retries и параллельные задачи подчиняются общему limiter/бюджету,
  Retry-After/backoff. Рабочая конфигурация очереди — 40 RPM / окно 4;
  это не обещанный лимит источника. Один Airflow pool не заменяет pacing.
- Нужны checkpoints/resume по играм/разделам, replay без дублей и readback
  одинакового логического снимка трёх ODS. Не скрывать drift/partial/errors.
- Для профилей использовать достаточные встроенные публичные данные;
  отдельные N HTTP нужны только при недостатке полей и не являются ускорением.
- Через XCom передавать ссылки и малые манифесты, а не большие JSON.
- Сравнение — воспроизводимые одинаковые входы, загрузка/объём/чтение.
  Не строить универсальную платформу, SQL-движок для S3 или CDC без необходимости.
  Garage 2.4.1 игнорировал условные PUT: CAS на них не строить.

## Код, архив, проверки и Git

- Перед работой читать docs/HANDOFF.md, docs/REPOSITORY_STRUCTURE.md,
  DATA_MODEL.md, DAGs.md и SOURCE_CONTRACT.md по затрагиваемой области.
- Текущие DAG используют entity_* и connections.py. legacy/ и совместимые
  ods.py/storage.py/repack.py сохраняют старые форматы для прежних тестов/replay.
  Новых зависимостей production от legacy не добавлять.
- archive/ — исследовательские прототипы, не импортировать в рабочий код/DAG/образ.
  Не запускать массово: некоторые выполняют HTTP при импорте.
- Локальные data/, exports/, staging и backup не включать в Git/Docker context.
  Исторические evidence/CSV/JSON/checksums не удалять и не переписывать.
- Не писать секреты в Git, URL, логи, отчёты, манифесты или команды.
  Проверять наличие ключей без вывода значения. .env.example — только заглушки.
- Выбирать простые конкретные функции/загрузчики; не переписывать всё ради
  архитектуры и не добавлять универсальные плагины без подтверждённой необходимости.
- Проверять повторы, частичные загрузки, пагинацию, v2/v3, историю A→B→A,
  восстановление JSON, pause/resume и согласованность трёх ODS.
  Не выдавать skipped интеграционные проверки за пройденные.
- Проверять реальное окружение: старые PID/счётчики/сведения о Docker не актуальны
  автоматически. Различать факт, гипотезу, план и ограничение окружения.
- Перед Git-операциями проверять состав файлов и исключения.
  Публикация/push без соответствующего запроса пользователя не разрешены.
