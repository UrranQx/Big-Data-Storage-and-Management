# Компактное хранение повторных наблюдений: проверка варианта

**Статус после уточнения пользователя:** этот прототип не выбран как новая
схема. Основное решение — предметные наборы игр, ранов и игроков, описанные
в актуальном начале `DATA_MODEL.md`. Прежний сбор остановлен. Нижеследующее
сохраняется как результат эксперимента, не инструкция к автоматическому внедрению.

Уточнение пользователя: пример `run_id — время — имя — дата верификации`
не задаёт обязательную схему. Сохраняем полный JSON, все таймеры/статусы/роли,
историю изменений, повторные свежие проверки и происхождение.

Причина задержки текущего Minecraft — 3 660 931 отдельных наблюдений профилей,
сформированных из повторяемого playerList. Для полного runs-пакета создано
3 776 627 записей. Каждая отдельно загружается и читается обратно, а для S3
ещё предварительно проверяется существование объекта. Финализатор затем
повторяет полную проверку. Это выбранная реализация, не требование ЛР1.

## Проверяемое изменение

Четыре логических набора сохраняются. Вместо отдельного документа на каждое
появление объекта хранится один документ на сочетание:

`snapshot + source + API + entity_type + entity_id + payload_hash + context`.

Внутри — компактные тройки `[response_id, path, observed_at]`. Полные payload
и ответы не изменяются. Прежние поля сущности, проекция и контекст не сливаются
с другими состояниями. Из списка точно восстанавливаются исходные observation
ID и все поля каждого прежнего наблюдения. A → A и A → B → A остаются
различимыми; историю нужно читать по времени событий, а не по порядку групп.

Это группировка физического хранения истории; записи исходных состояний не
затираются. Она уменьшает количество отдельных операций, но ссылки на каждое
появление по-прежнему занимают место. Дополнительное сжатие списков одинакового
состава можно оценить отдельно, без потери порядка исходных массивов.

## Что уже реализовано и проверено

`src/speedrun_etl/repack.py` создаёт новый изолированный пакет из существующего,
без запросов API, изменения исходного пакета или работающих ODS. Каждый
восстановленный observation сверяется с исходным digest; ответы восстанавливаются
с проверкой body_digest. Непустой целевой каталог не перезаписывается.

Синтетический тест: повторная проверка, A → B → A, перестановка профилей,
неизвестные поля и неизменность исходного пакета. Реальный тест — два ответа
Minecraft категории mkeyl926:

- `31808e2c-d379-4812-951f-10b061fd9ba8`, страница 2;
- `4823a210-b457-4875-a56c-1d46635e9075`, повторная проверка страницы 1.

Каждый содержит 100 ранов, 8 272 профиля, одну платформу. Верная сумма —
**16 746** исходных наблюдений (раньше в объяснении ошибочно указано 16 546).
Новый пакет содержит **8 473** групп наблюдений: 8 272 профиля, 200 ранов,
одну платформу. Все 16 746 наблюдений восстановлены без изменения; оба
ответа восстановлены. Проверка заняла 12,587 с; это время локальной
перепаковки двух ответов, не замер загрузки хранилищ или прогноз всего снимка.
Вместе с payload/responses/manifest получается 16 951 запись вместо 25 224.

Результат находится в state-volume:
`experiments/grouped-v2-minecraft-two-pages-001-result.json`.

## Граница готовности

Это изолированный прототип, **не подключённый к рабочим DAG**. Текущие
loaders/verify/history/players ожидают прежние observation и потребуют
совместимого чтения групп перед переключением. Отдельно нужны пакетные
чтение/запись PG/Mongo, устранение второй полной проверки финализатора и
проверка ограничения размеров BSON. Прототип явно отклоняет группу больше
8 МиБ: перед production такой список нужно разделять на блоки.

Менять работающий snapshot в процессе загрузки нельзя: его digest и receipts
должны продолжать соответствовать одному формату. Перепаковку полного снимка,
три загрузки и сравнение старого/нового результата выполнять в новом namespace.
Исторические измерения относятся к старому формату и не подтверждают скорость
нового. Параллельность регулируется и pool, и общим Airflow parallelism;
увеличение только одного параметра не запустит три загрузчика одновременно.
