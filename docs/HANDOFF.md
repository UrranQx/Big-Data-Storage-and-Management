## Границы и открытые решения

ЛР1 — ODS, Airflow, три разных сервиса, ≥3 DAG, замеры и отчёт. Нужны простая
и воспроизводимая реализация, проверки сбора и возможность демонстрации.
Последнее уточнение пользователя: простота реализации не означает ограничение
данных одной игрой. Нужен свежий сбор глобального каталога и максимально доступных
данных всех игр через итоговый процесс, без использования старых профилей
в качестве готового результата. Одна игра — этап проверки перед масштабированием.
Нужны оценка бюджета запросов и объёма, продолжение глобального обхода и
разумное обновление. Пользователь рассматривает удаление накопленного,
но состав очистки ещё не утверждён — ничего пока не удалено.
Отдельный запрос каждого профиля, распределённый limiter, все таблицы черновой
ODS и benchmark-фреймворк сами по себе не обязательны. Проверенный код
прототипов можно переносить и адаптировать; старые данные не подменяют новый сбор.
Последнее уточнение о хранении: для будущих анализов нужна история любых
собираемых сущностей, не только рекордов. Полные исходные поля, изменившиеся
состояния и их происхождение сохраняются уже в ЛР1; нормализованная история
и расчёты относятся к ЛР2. Повторный запуск не размножает сущности/payload;
fresh check и retry различаются. Не предрешать файловый raw + manifest или
полные копии каждого запуска. Требования — «История без дублей»
в `SOURCE_CONTRACT.md`; физическую модель ещё предстоит утвердить.
Не нужны DDS, SCD, расчёт PB/WR, витрины, Superset или OpenMetadata до их этапов.
Пользователь отдельно уточнил: **пользовательский сайт не нужен ни в одной
лабораторной; не оверинжинирить**. Twitch/YouTube, карты эмбеддингов,
рекомендации и уведомления — только идеи за пределами текущей реализации.

Решить при планировании: тройка хранилищ с аргументацией, минимальный ODS,
доступные ресурсы Docker, версии/совместимость Airflow, область демонстрации,
профильный endpoint, общий лимит, снимки/повторы, критерии честных замеров.
PostgreSQL + ClickHouse + MinIO можно рассмотреть первым вариантом, но это
рекомендация для обсуждения, не утверждённый стек. В старых документах есть
другая рекомендация PostgreSQL + MongoDB + MinIO — она тоже не утверждена.

В прежней сессии Docker CLI/Compose были доступны, Engine не работал.
Состояние на новой машине/в новой сессии проверить заново. Не раскрывать
`SPEEDRUNCOM_API_KEY`. Создание/публикация удалённого GitHub-репозитория
пользователем ещё не запрошены; локальная инициализация Git запрошена.

Полные значения и детали не дублировать из памяти вместо чтения манифестов.
При отсутствии локальных данных на свежем клоне опираться на отчёты как
свидетельства прошлого исследования, а текущую работу проверять заново.
