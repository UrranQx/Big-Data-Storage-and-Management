# Утверждённый план ЛР1

Пользователь передал план «Сбор Speedrun.com в три ODS-хранилища» и поручил
реализацию 2026-10-15. Этот документ фиксирует утверждённые решения; прежние
варианты стека/ODS в черновиках им уступают. Фактические результаты проверки —
в [отчёте](../reports/lab1/REPORT.md).

## Этапы и остановка

1. Зафиксировать контракт: этот файл, DATA_MODEL, DAGs, SOURCE_CONTRACT.
2. Compose: Airflow, три хранилища, постоянные volumes, проверка здоровья/UI.
3. Общий ETL: клиент, восстановимый ODS, checkpoints, конкретные загрузчики.
4. Малый e2e: свежие метаданные Portal; full-game `Inbounds`, ID из ответа;
   первые две страницы new/verified/rejected (или весь меньший раздел),
   stats до/после, первая страница WR history, встроенные профили участников.
   **До 30 HTTP-попыток на всю цепочку**, включая retries и проверки границ.
   Категорию не подменять. Старые raw/профили не использовать.

**После малого e2e обязательная остановка для просмотра пользователем.**
Полную Portal и глобальный сбор до разрешения продолжить не запускать.
Глобальная цель сохраняется; одна игра — только проверочный этап.

Уточнение пользователя 2026-10-16: разрешён следующий полный сбор одной игры
Half-Life для проверки. Он имеет отдельный collection/snapshot ID и жёсткий
предел 300 HTTP-попыток. Глобальный обход этим разрешением не охвачен.
Повтор загрузки того же пакета идемпотентен; новый свежий опрос добавляет
observations с новым response_id, но не дублирует содержимый payload.

5. Полная Portal: все доступные full-game категории, включая архивные;
   три статуса, obsolete; все доступные WR-страницы по базовым фильтрам.
6. Свежий глобальный каталог, пилот, прогноз ресурсов и сохраняемая очередь.
7. Проверки сбоев и воспроизводимый эксперимент трёх хранилищ.
8. Отчёт, CSV/графики, обоснованный выбор и инструкция демонстрации.

## Стек и ресурсы

Airflow 3.3.2/Python 3.11/LocalExecutor, parallelism=2: scheduler, api-server,
dag-processor, одноразовый init. PostgreSQL 16 с отдельными пользователями
и базами airflow, speedrun_ods, speedrun_control. MongoDB Community 8.0 без
replica set и с небольшим cache. Garage 2.4.1, один узел, replication factor 1.
Клиенты psycopg/pymongo/boto3, точные версии из constraints Airflow.
Образы закрепляются по digest, совместимость проверяется сборкой.
Linux-контейнеры Docker Desktop, около 8 ГиБ на стенд; настройки RAM/диска
автоматически не менять. Control и Airflow metadata не включать в замеры ODS.

Версии проверены по [Airflow prerequisites](https://airflow.apache.org/docs/apache-airflow/3.3.2/installation/prerequisites.html),
[constraints 3.3.2/3.11](https://raw.githubusercontent.com/apache/airflow/constraints-3.3.2/constraints-3.11.txt)
и [Garage quick start](https://garagehq.deuxfleurs.fr/documentation/quick-start/).
Копия constraints сохранена в infra/.

## Четыре набора ODS

| Набор | Ключ | Содержание |
|---|---|---|
| payloads | json-v1 + SHA-256 | Полные JSON-объекты, оболочки или блоки |
| responses | response_id | API, endpoint, параметры, времена, HTTP, оболочка и ссылки |
| observations | hash(response_id, entity_type, path) | Сущность, payload, происхождение, observed_at, контекст |
| manifests | snapshot_id + revision | Область, входы, версии, coverage, ошибки, counts/digest |

Сущность: `(source_system, entity_type, source_id)`; API v1/v2 — происхождение.
Без собственного ID — владелец и путь; гости только в контексте рана/позиции,
по имени не объединяются. Каждый DAG имеет snapshot_id; collection_id
связывает цепочку с явными входными снимками. Снимок — интервал, не атомарное
состояние сайта. Отдельных нормализованных таблиц предметной области нет.

Объекты известных списков игр/ранов/профилей/справочников выделяются по ссылкам.
Оболочка, неизвестные поля, порядок и повторы массивов сохраняются. Ран целиком:
участники, автор/проверяющий, таймеры, даты, переменные, obsolete/orphaned,
комментарии. Канонизация json-v1 сортирует ключи, сохраняет точные числа через
Decimal, различает отсутствие и null; пробелы/порядок ключей не новая история.
Восстановление обязано давать эквивалентное JSON-значение.

Физически — четыре PostgreSQL-таблицы (JSONB и типизированные поля ответов/
наблюдений), четыре MongoDB-коллекции с `_id`, четыре S3-префикса.
Индексы PG/Mongo: история сущности и snapshot/game/category/status.
S3-история — по префиксу сущности, фильтрация JSON клиентская, без SQL-движка.
Вне общего точного JSONB/BSON-подмножества — явно помеченный канонический
UTF-8 JSON одинаково в трёх сервисах. Большие payload разбиваются на блоки:
5 МиБ исходных байтов, менее 8 МиБ после base64 и ниже 16 МиБ BSON.

Players повторно использует исходные профильные observations, не меняя время,
response/type/path и ключ. Собственный manifest содержит выбранные observation
keys и входной runs snapshot. `observations.snapshot_id` — снимок обнаружения;
членство в производном профильном пакете задаётся manifest. Исходные responses
остаются в явно указанном входном снимке. Все отличающиеся проекции сохраняются.
Страна может отсутствовать; автор/проверяющий не подменяют участников.
Недоступность профиля — диагностика. При нехватке встроенных полей допустима
проверка до трёх ID в бюджете e2e; неизвестный endpoint массово не исследовать.

## История и надёжность

Успешный ответ сохраняется атомарно с fsync в staging до продвижения checkpoint.
Retry использует прежние ключи. Свежая проверка — новый response ID/время даже
при прежнем payload. A→B→A: два содержимых и три наблюдения. 404/исчезновение
не удаляют историю. Потеря несохранённого ответа может потребовать нового HTTP;
exactly-once на стороне API не обещается.

Загрузка: payload → responses → observations → manifests → чтение обратно,
сверка ключей/содержимого/digest → receipt сервиса. Общая ready только после
трёх подтверждений. Частичные загрузки дозагружаются по тем же ключам без сети
источника; распределённой транзакции нет. Payload/наблюдения/ответы/manifests/
evidence хранятся весь проект без TTL; технические логи — 30 дней.
Только новые временные staging можно очищать через 7 дней после трёх receipts
и проверки восстановления. В первом e2e очистка отключена. Старые данные и
архивы не удалять. Секреты исключены из Git, URL, логов и отчётов.

## DAG и сеть

games_metadata → runs → players, зависимости по конкретному snapshot ID.
Каждый: initialize → collect/package → три load-ветви → finalize.
Дочерние run ID детерминированы. Manual schedule, catchup=False,
max_active_runs=1, Airflow retries=2. XCom — маленькие ID/URI/digest/счётчики.
Импорт не обращается к сети. Source pool=1, load pool=1.

Общий клиент: последовательный HTTP, flock на общем Linux-volume, lock
охватывает ожидание и запрос. Между началами минимум 3,1 с, next_at сохраняется;
неизвестное/незавершённое состояние после сбоя — 60 с паузы. Timeout 60 с,
до пяти сохраняемых попыток на запрос, общий бюджет включает retries.
429: Retry-After число/HTTP-date, минимум 60 с; сеть/5xx: backoff+jitter.
Airflow retry не обнуляет бюджет. Все сетевые команды к источнику в контейнере
с этим volume, архивные сборщики параллельно не запускаются.

Coverage отдельно от технического успеха: verified_public_partitions, partial,
unavailable, not_checked. Намеренное ограничение e2e помечается явно.

## Полная область и управление после остановки

Свежий каталог v2 без фильтра типа. Основные игры: все доступные full-game
категории, включая архивные; new/verified/rejected; obsolete=1, video=0,
emulator=1, values=[]; без IL/challenges/отдельных Category Extensions.
Неизвестный тип — unknown, название не доказательство. Orphaned сохраняется.
V1-аудит выключен. Stats до/после. WR history — страницы каждой категории,
базовые фильтры записаны, комбинации переменных не перебираются.

Checkpoint по каталогу/игре/category×status/странице. Завершённые разделы не
перечитываются. Resume незавершённого проверяет первую/последнюю страницы
по ID/пагинации. При дрейфе один новый проход раздела, старые наблюдения остаются;
дальнейшая нестабильность — partial. В конце — граничные проверки. Проверять
page/length/count/pages, уникальность ID, game/category/status/отсутствие IL.
Границы не доказывают атомарность/полноту сайта.

Глобальный CLI через Airflow API: одна цепочка игры за раз, очередь/control
в PostgreSQL, присоединение к существующим DAG runs после рестарта. Ошибка игры
остаётся для повтора; сбой ODS приостанавливает сеть. Обновление выбранной очереди
с новым collection_id; каталог не чаще недели; приоритет незавершённым/new,
далее время последней проверки, с ротацией старых игр. Date-фильтры не применять
до доказательства. Ежедневную актуальность всех игр не обещать.

Исторические 52 030 игр/261 страница — ориентир. После свежего каталога пилот
до 20 основных игр: по пять из четырёх групп по порядку величины счётчика,
выбор по стабильному hash ID. Измерить запросы/страницы/retries, HTTP-время,
байты, уникальные payload/наблюдения, staging/ODS. Прогноз по группам с диапазоном
и вкладом крупных игр, пересчёт каждые 100 игр. Нижняя граница R/20 минут.
Сеанс до 8 часов или 9000 попыток; при свободном месте <max(10 ГиБ,20% диска)
пауза без очистки. Перед масштабированием показать прогноз пользователю.

## Проверки, эксперимент, приёмка

Проверить retry/A→A/A→B→A, восстановление точных чисел/NULL/неизвестных полей/
повторов, перестановку объектов, пустые/последние страницы, дубли/дрейф/фильтры,
rejected-only/командных/гостевых/недоступных участников, разные роли, limiter
между процессами и перезапусками, обе формы Retry-After, частичную загрузку,
resume, одинаковые ключи/digest/восстановленные ответы, сохранность после 404.

Эксперимент после полной Portal: один свежий пакет с фиксированным digest;
при небезопасном объёме детерминированный поднабор до 10 000 ранов со связями.
Три загрузки в изолированные namespaces, чередовать сервисы, схема/индексы
до измерения, без сети источника. Время и records/s, логический/физический
объём/индексы где доступны, идемпотентная загрузка, чтение 100 фиксированных ID
и истории (первый и два повторных прохода), фильтр game/category/status
SQL/Mongo и клиентским S3 с оговоркой стоимости. Первый проход не гарантированно
холодный кеш. CSV, медианы/разброс, графики загрузки и объёма. Гипотеза выбора:
PostgreSQL основной ODS, S3 архив; окончательный вывод после замеров. При близких
результатах предпочтение SQL/целостности PG. Другие копии не удалять.

Приёмка: Compose/UI, три сервиса одного снимка, три разных ETL, восстановимые raw,
история, resume/coverage, замеры/графики/выбор, отчёт/демонстрация. GitHub/push
отдельно по запросу. DDS/SCD/DQ DAG/PB-WR расчёт, витрины/Superset/OpenMetadata,
сайт/API, Twitch/YouTube/ML, Kafka/Kubernetes/dbt сейчас исключены.
Защита темы/таблица источников не требуют действий. Полнота сайта и история
до начала наблюдений не гарантируются.
