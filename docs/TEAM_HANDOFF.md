# Запуск проекта на другом компьютере

Актуализация 28 октября: перед длительным сбором нужен монитор реального диска
Docker на хосте: `python -u infra/host_disk_watch.py`. Для нестандартного пути
VHDX или Linux передать `--path`; инструкция в infra/README.md. Резерв по
умолчанию 20 ГиБ, измерение каждые 30 секунд; старше 120 секунд — безопасная
остановка новых HTTP. `batch --all` без свежего измерения не начинает сбор.
RPM по умолчанию теперь 40, это наш потолок, а не подтверждённый лимит API.

Для новых пакетов большие playerList (от 1000 профилей) хранятся общим
сжатым фрагментом и ссылкой в каждом ответе. Полный JSON восстанавливается;
различающиеся состояния, порядок/повторы массива и история профилей сохраняются.
Повторная обработка одинакового списка сокращена до первого/последнего ответа
серии; для повторяющихся ID внутри списка это сокращение выключено. Сеть и
исходный HTTP-journal этим не сокращаются. Старые пакеты читаются прежним codec.

При стабильном недоборе date-large автоматически проверяется весь этот раздел
без дат с отдельными checkpoints; исходная диагностика остаётся в manifest.
Отсутствие full-game категорий получает состояние очереди not_applicable после
подтверждения трёх ODS и не блокирует следующую игру. Неизвестная классификация,
ошибки фильтров/ODS/бюджета остаются ошибками.

ЛР1: Airflow 3.3.2 / Python 3.11, PostgreSQL 16, MongoDB 8.0, Garage S3 2.4.1.
Три DAG: games_metadata → runs → players. Основные наборы ODS: карточки игр,
версии ранов и профилей, WR-история; исходные ответы и компактные checks сохраняют
происхождение и изменения. Отдельные появления неизменного профиля не размножаются.

## Что передаётся

Для одной конкретной игры каталог не нужен. Только карточка и метаданные:

```powershell
docker compose exec -T scheduler python -m speedrun_etl.cli start-game --collection team-portal-card-001 --game portal --metadata-only
```

Полная цепочка одной игры с явным ускорением крупных разделов:

```powershell
docker compose exec -T scheduler python -m speedrun_etl.cli start-game --collection team-subway-001 --game subsurf --runs-strategy date-large --request-budget 5000
```

Можно указать --game-id вместо --game. Новая очередь топ-10 с той же стратегией:

```powershell
docker compose exec -T scheduler python -m speedrun_etl.batch run --collection team-top10-date-001 --top 10 --runs-strategy date-large --continue-on-drift
```

Каталог один на batch; --top 1 тоже требует каталог для выбора по рейтингу.
date-large применяется при >10000ранов и >=5000встроенныхпрофилей и release year,
иначе обычная пагинация; --metadata-only не создаёт runs/players. Default=standard.
Стратегия запоминается при resume; у начатой коллекции её не менять. Новые режимы
проверены на пустом staging/трёх отдельных ODS с фикстурами и свежими HTTP малой
игры. Полный свежий top10/date-large не проверен. Существующие volumes не удалять
ради проверки. Прежнее состояние живого сайта и утраченную историю наблюдений
свежий HTTP не воспроизводит.

На 28 октября top10 завершён10complete/0partial после repair Subway по датам;
40678verified/49767rejected проверены, три DAG/три ODS/аудит прошли. Ограничения
WR остаются в манифестах; подробности в HANDOFF/progress. Каждый scope=game получает только карточку своей игры,
общий каталог собирается один раз перед очередью. Его готовый снимок раньше
повторялся в тексте мониторинга, это не были повторные сетевые обходы.

Для явного ремонта неполных разделов уже существующей очереди:

На авторском стенде приведённый repair уже завершён; повторять его не нужно.

```powershell
docker compose exec -T scheduler python -m speedrun_etl.repair --batch lab1-top10-20261027 --game-id y65797de --collection lab1-subway-repair-20261028 --request-budget 2500
```

На другом компьютере сначала нужен собственный batch со своими снимками;
приведённые ID не переносят данные автора. Для новой попытки выбрать новый
collection; для продолжения использовать прежний. CLI сохраняет готовые
разделы/WR и историю, запускает только недостающие разделы через три DAG,
проверяет три ODS и аудит, затем обновляет очередь. Date-фильтры уменьшают
playerList, но меняют place/obsolete; контекст сохранён отдельно. Обычный
batch на этот эксперимент автоматически не переключён. Во время repair
наблюдать тем же progress --batch ... --watch 30; данные/volumes не сбрасывать.

Git bundle содержит историю Git; ZIP — исходники того же коммита. Docker volumes,
наши выгрузки и секреты не передаются. У коллеги будет собственный свежий каталог,
свежие HTTP-запросы и новые данные во всех трёх ODS. Полные выгрузки с нашего
компьютера для запуска не нужны. Не переносить чужие .env и garage.local.toml.

При передаче bundle:

```powershell
git clone ./speedrun-etl-handoff.bundle ETL_practice
cd ETL_practice
```

ZIP достаточно распаковать и открыть терминал в каталоге с compose.yaml.
Для работы нужны Docker Desktop с Linux-контейнерами и около 8 ГиБ доступной
Docker RAM; проверить свободный диск перед большим сбором. Python нужен для
генерации настроек; весь ETL запускается внутри Linux-контейнеров.

## Первый запуск

```powershell
python infra/configure.py
docker compose config --quiet
docker compose build init
docker compose up -d --no-build
docker compose ps -a
```

Собирать только init: все Airflow-сервисы используют один образ. Генератор
создаст собственные секреты и откажется перезаписывать существующие настройки.
Дождаться healthy у сервисов, у init ожидается Exited (0).
UI: http://localhost:8080, пользователь admin, пароль AIRFLOW_ADMIN_PASSWORD
из локальной .env. API-ключ Speedrun.com не требуется.

Проверка без обращений к Speedrun.com:

```powershell
docker compose exec -e ETL_INTEGRATION=1 scheduler python -m unittest discover -s /opt/project/tests -v
docker compose exec scheduler airflow dags list-import-errors
```

Тесты реальных хранилищ создают небольшие test_* пространства. Их не смешивать
с рабочей схемой/БД entity_v2 при оценке объёма. Архивные скрипты не запускать.

## Свежий каталог и топ-10

```powershell
docker compose exec -d scheduler python -u -m speedrun_etl.batch run --collection team-top10-001 --top 10 --log
```

Драйвер сам получает карточки всех игр, проверяет каталог в трёх ODS, определяет
топ-10 по свежему счётчику GetGameSummary.stats.totalRunsFG и запускает по одной
цепочке игры: метаданные → все доступные full-game категории со статусами
new/verified/rejected и obsolete → WR-история → профили участников. Level runs
не собираются. Категории, фильтры, диагностика и ограничения остаются в manifest.
Встроенные профили используются без отдельного запроса на каждого игрока.

Рейтинг по счётчику сайта не является независимым пересчётом verified ID.
Карточки проверяются по type и gameTypeIds. Category Extensions исключаются
по gameTypeIds=8, а не названию или одному baseGameId. Неизвестные значения
останавливают отбор. Это проверенная политика текущего v2, не доказательство
полноты всего сайта. Основание enum и живой пример описаны в SOURCE_CONTRACT.md.

При дрейфе count/pages сборщик продолжает доступные страницы и сохраняет
partial с диагностикой. Изменения граничных ID при стабильном счётчике
допускают один повтор раздела. Ошибки фильтра игры/категории/статуса остаются
техническими ошибками, а не успешным сбором. По умолчанию partial останавливает
очередь. Опция --continue-on-drift позволяет продолжить другие игры после
подтверждения трёх хранилищ, сохраняя известные дрейфующие разделы в
entity_batch_queue.details.coverage_retry. Это список для последующей проверки,
не автоматически выполненный добор. При возобновлении использовать тот же флаг.
Сбои DAG/ODS и исчерпание бюджета продолжают останавливать очередь. Итог с
пробелами называется complete_with_gaps; монитор отдельно показывает
processed/complete/partial и конкретные разделы для повторной проверки.

Если упала только загрузка одного хранилища, collect очищать не нужно.
После исправления загрузчика в Airflow повторить упавший load и его downstream
в том же DAG run: например, load_mongo → finalize → needs_child → trigger_players.
Успешные collect и загрузчики других ODS оставить завершёнными. Повтор использует
прежний пакет и устойчивые ключи. Если после восстановления драйвер остановится
с coverage_paused, это отдельное ограничение исходного сбора, а не новый сбой записи.

WR сохраняется для каждой full-game категории с базовыми фильтрами, values=[].
Комбинации переменных не перебираются: это не история всех подкатегорий сразу.
Пустой объект ответа — unavailable; отсутствие пагинации не доказывает полноту.
Даты событий WR сохраняются как исходные, собственная реконструкция WR не выполняется.

Каталог имеет бюджет 650 HTTP-попыток, рейтинг — 500, одна игра — 5000,
включая retries и проверки границ. Изменить бюджет до старта можно аргументом
--game-request-budget 10000. При исчерпании данные остаются partial, очередь
останавливается. Не обходить лимит сменой настроек существующего снимка.

По умолчанию через 8 часов драйвер перестаёт начинать новые игры и завершает
активную. Для продолжения выполнить ту же команду с тем же ID и параметрами:
готовые игры пропускаются, каталог и выборка не запрашиваются заново. Новый
ID означает новый свежий сбор, старые сущности не затираются.

Для полного доступного каталога вместо рейтинга:

```powershell
docker compose exec -d scheduler python -u -m speedrun_etl.batch run --collection team-all-001 --all --hours 8 --log
```

Это длительная очередь, а не обещание завершить весь сайт за один сеанс.
Топ-10 на стенде автора запущен 2026-10-27 после проверок; завершение смотреть
через progress. Полная очередь всех игр пока не запускалась.

## Прогресс, остановка и возобновление

```powershell
docker compose exec scheduler python -m speedrun_etl.batch status --collection team-top10-001

docker compose exec scheduler python -m speedrun_etl.progress --batch team-top10-001 --watch 30
docker compose exec scheduler tail -f /opt/airflow/state/batches/team-top10-001/driver.log
```

Ctrl+C в watch/tail прекращает только просмотр. Мониторинг показывает, жив ли
драйвер (по файловому lock, а не устаревшему PID), этап каталога/рейтинга/игры,
сохранённую причину остановки, страницы и завершённые разделы. До построения
рейтинга список игр ещё не выбран. --json даёт машиночитаемый отчёт;
для отдельной игры доступны progress COLLECTION --human --watch 30.
Это чтение локального состояния/control DB, без запросов к Speedrun.com.
Драйвер пишет heartbeat прогресса каждые 60 секунд даже без смены DAG state.
Перед стартом каждой цепочки проверяется свободное место: минимум большее
из 10 ГиБ и 20% staging-диска. Автоматической очистки данных нет.
Для каждой игры
в status выводится collection_id; его можно передать в speedrun_etl.progress.
Подробный прогресс виден в Airflow: DAG → запуск → collect → Log.
Runs пишет категорию/статус, страницу и число уникальных ранов; WR — категорию,
страницы и диагностику; упаковка — число ответов/версий; Players — просмотренные
версии ранов/профилей, найденных участников и недоступные профили.
HTTP-лог показывает бюджет, фактические запросы/мин, время ответа и ожидание
pacing. В speedrun_etl.progress есть компактная HTTP-телеметрия без чтения raw.

Обычная остановка: docker compose stop. Volumes сохраняются. После up -d
выполнить ту же batch-команду; не запускать два драйвера с одним ID — второй
будет ждать lock. При failed DAG очередь останавливается. В UI изучить ошибку,
исправить причину и очистить failed collect/загрузчик с downstream, затем
повторить batch-команду. Уже сохранённые HTTP-ответы/checkpoints используются.
Пять HTTP-попыток на один запрос сохраняются между retries и не сбрасываются:
при их исчерпании нужна диагностика, а не бесконечное нажатие retry.
Не применять down -v для штатной остановки: это удалит данные.

Исправленный рейтинг имеет отдельный ID COLLECTION-ranking-v2. Для старой
очереди с неверно включёнными CE предусмотрен --refresh-selection после
просмотра нового рейтинга: заменяются только pending-игры, прежняя запись
помечается excluded и сохраняется. Начатая цепочка остаётся с исходным
snapshot ID и checkpoints. Попытка исключить уже начатую игру отклоняется.
Обычное продолжение готовой исправленной очереди этого флага не требует.

## Частота запросов

По умолчанию общий последовательный pacing проходит ступени 30 → 45 → 60/мин.
В .env можно установить ETL_MAX_RPM=90 до старта: добавятся ступени 75 и 90.
Это экспериментальный потолок, не подтверждённый лимит API v2. После 420/429
соблюдаются Retry-After и минимум 60 с паузы, потолок снижается до 20/мин.
Через 5 минут и 20 чистых ответов начинается проба 25/мин; далее +5 после
минимум 2 минут и 20 чистых ответов, до ETL_MAX_RPM. Новый 429 снова даёт 20.
Состояние восстановления сохраняется на общем volume.
Новый предел требует пересоздания Airflow-контейнеров; не делать это посреди
сбора без планируемого возобновления. Ограничитель общий для одного стенда,
не распределён между компьютерами — согласовывать параллельный сбор под одним IP.

В runs по умолчанию ETL_PAGE_CONCURRENCY=4: до четырёх страниц в полёте,
с единым pacing/budget и полным сохранением ответов. Это не множитель RPM.
Для диагностики можно установить 1 (последовательно) или 2; настройка
применяется в новых процессах задач. Контролируемое продолжение после clear
использует прежние checkpoints и проверяет границы незавершённого раздела.
На новых SM64-страницах окно 4 дало 20,1 с против 44,1 с последовательно;
это результат небольшого эксперимента, а не гарантия для каждого endpoint.
HTTP-лог показывает recent_rpm по 10 запросам и mean_rpm_60_requests по 60,
изменения потолка Rate: ceiling=... и режим cooldown/probe/adaptive.

HTTP gzip включён и сохраняет точный JSON после распаковки. На реальной странице
Minecraft ответ уменьшился с 1 288 351 до 213 161 сетевых байтов, но занял около
16 с. В наблюдавшемся окне было ~3,7 запроса/мин при pacing 1 с: повышение
потолка не сокращает такое ожидание ответа. limit=200 сайт проигнорировал,
поэтому размер страницы принудительно не увеличивается.

## Что подтверждено и что ещё предстоит

Полные свежие цепочки Half-Life и Minecraft прошли три DAG и три ODS. При
восстановлении 2026-10-27 подтверждены завершённые состояния Minecraft:
46 256 уникальных leaderboard ID, 33 раздела, 19 195 профилей, 546 запросов;
WR-ответы 11 категорий (2 недоступны). Ранее также проверен отдельный smoke:
400 ID ранов, 8468 профилей, 7 ответов, обычный/пустой WR. Во всех трёх ODS
smoke readback/replay совпали. Свежий Portal e2e/replay/audit от 27 октября
также прошёл; после ускорения HTTP выполнены 59 тестов. На другом компьютере выбрать собственный ID
для новой очереди; завершение топ-10 пока не подтверждено.

Код, инструкции и небольшие доказательства есть в Git; исходные данные и секреты
игнорируются. Финальный benchmark нового формата и полный отчёт ещё требуют
завершения; прежние CSV замеров относятся к старой схеме. Исторические
queue_driver.py/benchmark.py не использовать для нового прогона.
Состояние автора и ID — HANDOFF.md, предметный контракт — DATA_MODEL.md.
