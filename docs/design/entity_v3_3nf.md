# Проект нормализации ODS Speedrun.com до 3НФ

Предлагаемая схема `speedrun_3nf` содержит **30 предметных таблиц**. Она проектируется из восьми таблиц `entity_v3`. Полные карточки, HTTP-ответы, снимки и наблюдения хранятся в ODS.

[DDL PostgreSQL](entity_v3_3nf.sql) · [Полная ER-диаграмма Crow’s Foot в Mermaid](entity_v3_3nf.mmd)

## Живая выборка PostgreSQL

Через `docker compose exec postgres psql -U speedrun_ods -d speedrun_ods` выполнена команда `\dt entity_v3.*`. Для каждого имени из результата выполнен запрос `SELECT * FROM entity_v3.<TABLE> LIMIT 1` как подзапрос с сериализацией строки в JSON. Все восемь запросов вернули по одной строке. Ниже приведена структура выборки. Данные взяты без `ORDER BY`, поэтому примеры показывают форму строк и не подтверждают полноту распределения полей.

| Таблица ODS | Что видно в выборке | Использование в проекте |
| --- | --- | --- |
| `blocks` | Хеш блока и данные в Base64 | Чтение содержимого при извлечении из ODS |
| `checks` | Снимок, проекция, первое и последнее появление, последовательность состояний | Источник последовательности наблюдений при извлечении. Остаётся в ODS |
| `games` | Карточка с именем, датой релиза по частям, счётчиками и списками платформ, регионов, таймеров | `game`, `game_version`, справочники и связи версий |
| `manifests` | Формат, настройки и результат сбора, список входных снимков | Остаётся в ODS |
| `players` | ID, имя, URL, `areaId`, цвет и уровень полномочий | `player`, `player_version` |
| `responses` | HTTP-метаданные, параметры, тело и его SHA-256 | Исходные ответы остаются в ODS |
| `runs` | Категория, игра, статус, IGT, видео, участники, значения переменных, автор подачи и проверяющий | `run`, `run_version`, `run_participant`, `run_time`, `run_value`, `run_video` |
| `wr_history` | Фильтры запроса, страница, индекс события, дата выполнения, список из шести ID ранов | `wr_scope`, `wr_scope_value`, `wr_event`, `wr_event_run` |

Дополнительная выборка из `games` с `projection = 'game_detail'` вернула `game`, `categories`, `levels`, `platforms`, `variables`, `values`, `moderators`, `users` и `theme`. В отдельной строке `checks` с `unfiltered_leaderboard` поле `obsolete` оказалось булевым, а `place` строковым. Вложения читаются по кодеку пакета, поэтому путь `raw.value` применим к `native-json-v1`.

## Таблицы и зерно

### Игры и профили

| Таблица | Что представляет ключ строки |
| --- | --- |
| `game` | Исходный ID игры |
| `game_version` | Версия карточки или детали игры, включая название, параметры релиза и исходные счётчики |
| `platform` | Исходный ID платформы |
| `platform_definition` | Атрибуты платформы, наблюдаемые в конкретной версии метаданных игры |
| `game_platform` | Позиция платформы в массиве версии игры |
| `game_timer` | Позиция допустимого кода таймера в версии игры |
| `game_region` | Позиция исходного ID региона в версии игры |
| `category` | Исходный ID категории и подтверждённая игра-владелец |
| `category_definition` | Правила, название и прочие атрибуты категории в заданной версии метаданных |
| `game_level` | Исходный ID уровня и подтверждённая игра-владелец |
| `level_definition` | Название и прочие атрибуты уровня в заданной версии метаданных |
| `variable` | Исходный ID переменной и подтверждённая игра-владелец |
| `variable_definition` | Атрибуты переменной и ссылка на значение по умолчанию в конкретной версии метаданных |
| `variable_value` | Исходный ID значения и разрешённая родительская переменная |
| `value_definition` | Атрибуты значения в конкретной версии метаданных |
| `variable_category` | Явная связь определения переменной с категорией |
| `variable_level` | Явная связь определения переменной с уровнем |
| `player` | Исходный ID публичного пользователя, в том числе при отсутствии профиля |
| `player_version` | Наблюдаемое состояние профиля, включая исходный `areaId` |
| `game_moderator` | Позиция модератора и его исходная роль в конкретной версии игры |

### Раны и события WR

| Таблица | Что представляет ключ строки |
| --- | --- |
| `run` | Исходный ID рана, в том числе впервые встреченный в WR |
| `run_version` | Core-состояние рана, включая статус, даты и отдельные ссылки на автора подачи и проверяющего |
| `run_participant` | Одна позиция участника в версии рана. Допустимы несколько участников, гость или пустой список |
| `run_time` | Один таймер версии рана по имени исходного поля, с исходной строкой. Числовая длительность вычисляется при надёжном разборе |
| `run_value` | Одна позиция исходного `valueId` в версии рана |
| `run_video` | Одна позиция видео в версии рана |
| `wr_scope` | Условия зачёта для опубликованной истории WR по каноническому ключу |
| `wr_scope_value` | Одна позиция значения переменной в условиях зачёта |
| `wr_event` | Одно исходное событие в рамках зачёта, с датой выполнения при наличии |
| `wr_event_run` | Одна позиция рана в событии, включая несколько результатов в одном событии |

## Функциональные зависимости и допущения

- Массивы предметных связей разложены на строки. В `run_participant` ключ `(version_id, position)` определяет участника, а отображаемое имя зарегистрированного игрока хранится в `player_version`. В `run_value` позиция определяет `value_id`, а родительская переменная определяется самим `value_id`. Поэтому имя игрока и ID переменной в таблицах связей не дублируются.
- `category_id → game_id` для подтверждённой категории. Игра рана или фильтра берётся из владельца категории. Отдельный FK на игру заполняется при отсутствии категории. При конфликте ссылок исходные ID остаются в ODS. Для подтверждения владельца загрузчику понадобятся согласованные наблюдения.
- Принята область одного источника, Speedrun.com. ID категорий, уровней, переменных и значений трактуются как уникальные в пределах своего типа, а подтверждённый владелец считается стабильным. Ссылки на ещё не описанные ID могут создать строки идентичности с пустым владельцем или без версий. Подтверждение владения и проверка, что значение по умолчанию относится к своей переменной, входят в будущие правила загрузки.
- Каждая таблица версий использует собственный ключ. Порядок наблюдений и переходы вроде A → B → A можно восстановить по `entity_v3.checks`.
- Место и признак `obsolete` отдельного рана зависят от контекста выдачи и остаются в ODS. Для WR используется локальный ID события. Страница и индекс в исходной выдаче остаются в ODS. Совпадение зачёта и даты само по себе не устанавливает тождество двух событий. Связь WR с раном строится по ID. Полные вложенные данные рана и состав участников в конкретной выдаче доступны по ответу и пути. Из этих строк не выводятся периоды владения мировым рекордом.
- Прямое преобразование рассчитано на перечисленные в DDL атрибуты. Архив сохраняет незнакомые поля, точное исходное представление, тему оформления, вложенных пользователей из метаданных и специфичные варианты кодеков. Модель дат использует отдельные компоненты для неполной даты релиза. Временные отметки рана и профиля следует заполнять только при достаточной точности исходного значения.

DDL создан и выполнен в отдельном одноразовом PostgreSQL 16. Проверка подтвердила наличие 30 таблиц. Перенос строк и запуск DAG не входят в этот проект.
