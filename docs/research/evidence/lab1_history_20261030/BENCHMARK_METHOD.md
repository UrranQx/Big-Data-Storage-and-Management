# Сравнение ODS entity-v2

Выполненный эксперимент: [CSV всех измерений](entity_v2_benchmark_20261028/measurements.csv),
[вход и SHA-256](entity_v2_benchmark_20261028/input.json),
[завершение](entity_v2_benchmark_20261028/completed.json),
[график загрузки](entity_v2_benchmark_20261028/load_time.png),
[график объёма](entity_v2_benchmark_20261028/storage_size.png).
Прежние measurements.csv в корне reports/lab1 относятся к исторической схеме.

Вход — полный свежий Portal из трёх подтверждённых снимков
`lab1-top10-fresh-20261028-g-4pd0n31e-{games_metadata,runs,players}`.
Учитываются роли загрузки: внутренние кандидаты профилей из runs не добавляются
повторно поверх результата players. Одинаковые ключи объединяются только при
равном содержимом. 53 459 логических записей, 52 888 854 байта канонического JSON,
20 476 версий ранов, 6121 версия профилей, 244 исходных ответа.

```powershell
docker compose exec scheduler python -u -m speedrun_etl.benchmark --collection lab1-top10-fresh-20261028-g-4pd0n31e
```

На другом компьютере указать собственный завершённый collection. Модуль
отказывается работать при активных DAG/драйвере сбора. Общая source.lock
исключает запросы к Speedrun.com на всё время измерений; HTTP источника — 0.
Схемы и индексы создаются до отсчёта времени. Выполняются три повтора в новых
`test_bench_*` пространствах. Порядок сервисов циклически меняется. Тестовые
пространства сохраняются; production entity_v2 не очищается и не перезаписывается.

Измеряются:

- Загрузка существующими пакетными загрузчиками до readback всех логических
  записей и контрольного подтверждения; это не чистое время INSERT.
- Повторная загрузка того же пакета с проверкой числа строк и точного списка
  объектов S3; повторы не создают новые версии/объекты.
- Объём только тестовой ODS: PostgreSQL pg_table_size + pg_indexes_size;
  MongoDB storageSize + indexSize после fsync, отдельно dataSize;
  Garage — сумма тел объектов вместе с индексом снимка.
- История checks и последняя сохранённая версия в каждой проекции для
  100 одинаковых ID, выбранных по стабильному hash. Контексты не сливаются,
  собственные PB/WR не вычисляются.
- Один одинаковый фильтр game/category/status: SQL/Mongo на сервере, S3
  читает все блоки runs снимка и фильтрует клиентом. Совпадение результатов
  подтверждается digest.

Каждое чтение выполняется тремя проходами в каждом повторе. Соединения и
индекс снимка S3 переиспользуются; данные чанков не кешируются нашим клиентом.
Первый проход не считается гарантированно холодным. Медианы чтения в REPORT
рассчитаны по 9 проходам, медианы загрузки/объёма — по 3 повторам.

Airflow metadata и control DB не входят в размер ODS. Сумма тел объектов S3
не равна физическому объёму Garage volume с метаданными/выделенными блоками.
MongoDB и S3 используют сжатие, PostgreSQL включает свои индексы и служебное
выделение таблиц; сравнивается фактическая выбранная реализация, а не формат
байт-в-байт на диске. Показатели нельзя переносить на другой размер/кластер
без нового измерения.

После копирования CSV в отдельную папку отчёта:

```powershell
python reports/lab1/plot_results.py reports/lab1/entity_v2_benchmark_20261028/measurements.csv
```

Нужен matplotlib на хосте. Схема размещения результатов в контейнере:
`/opt/airflow/state/benchmarks/entity_v2_<timestamp>/`.
Вывод о выборе хранилища приведён в актуальном начале REPORT.md.

## Дополнительные запросы и операции с данными

`src/speedrun_etl/storage_workloads.py` — фиксированный дополнительный опыт
ЛР1. Он не изменяет схему production ODS и не разворачивает DDS. Из сохранённых
пакетов трёх игр строятся временные рабочие проекции для 1000, 10000 и 100000
ранов, вложенные поднаборы по hash ID. Полный raw каждого выбранного объекта
остаётся строкой `raw_json`; параметры запросов вынесены в типизированные поля
и JSONB/BSON `properties`. Ключи профилей включают игру и source ID: гости
не объединяются между играми по имени.

Для каждой игры/ID взято последнее наблюдавшееся состояние среди leaderboard
проекций с детерминированным разрешением равного времени. Это вход эксперимента,
не утверждение текущего места/PB/WR. Прежние состояния остаются в production.
`time_ns` заполняется только при точном представлении исходной строки целым
числом наносекунд int64. Непредставимые строки не округляются: поле null,
raw сохраняется, количество указано в input.json. Только сортировка по времени
исключает такие строки; группировки/связи/прочие проверки учитывают все ID.
Пустая дата остаётся отдельной группой в месячных counts и исключается из
временного окна. Это не реализация очистки дат или времени для будущего DDS.

```powershell
docker compose exec -T scheduler python -u -m speedrun_etl.storage_workloads --collections YOUR_PORTAL YOUR_MINECRAFT YOUR_SM64 --sizes 1000 10000 100000 --log
```

Использовать свои завершённые коллекции; все входные снимки проверяются по
receipts и фактическому digest локального пакета. Перед опытом требуется
отсутствие активных DAG/драйверов. Общая source.lock удерживается до окончания,
новых Speedrun HTTP нет. Результаты находятся в state/benchmarks/workloads_*.

В каждом из трёх повторов создаются новые `test_wl_*` схема/БД/префикс.
Порядок сервисов меняется. Сначала работают только PK, затем добавляются:
составной scope/time/key, GIN JSONB и массива участников в PG; соответствующий
составной, индекс поля документа и multikey в Mongo. У S3 вторичный индекс
запросов не строится — колонка indexed означает тот же этап опыта. Планы
`EXPLAIN ANALYZE BUFFERS`/`executionStats` сохраняются до и после. Кеш не
сбрасывается, поэтому разница фаз включает влияние кеша и не является чистой
оценкой одного индекса. Число просмотренных строк/документов помогает объяснить
разницу независимо от одного времени исполнения.

Каждая операция чтения — три прохода в каждом повторе (9 замеров):

| Операция | Одинаковый результат |
|---|---|
| batch_100 | 100 выбранных ID и полный raw, один пакетный запрос |
| scope_top_100 | Игра/категория/статус, 100 строк с наименьшим представимым time_ns; исследовательская сортировка, не WR |
| json_filter | Все ID с выбранным platform_id внутри properties |
| player_runs | Все ID, содержащие выбранного участника в массиве |
| monthly_counts | Число ранов по игре/статусу/месяцу, включая отсутствующую дату |
| cumulative_counts | Накопительная сумма месячных counts по игре/статусу |
| join_1000 | 1000 ранов с набором доступных профилей участников, включая пустое соответствие |
| offset_page / keyset_page | Одна и та же страница из середины набора по стабильному ключу |

PG/Mongo вычисляют запросы на сервере; Garage читает gzip JSONL и считает
в Python. Индекс манифеста S3 переиспользуется, кеша прочитанных чанков у клиента
нет. Полный результат материализуется внутри таймера, digest считается после.
Проверяются совпадение digest с локальным эталоном и между сервисами. Окна
Mongo используют [$setWindowFields](https://www.mongodb.com/docs/v8.0/reference/operator/aggregation/setWindowFields/),
связь — [$lookup](https://www.mongodb.com/docs/v8.0/reference/operator/aggregation/lookup/).
Это поддерживаемые операции, а не утверждение, что Mongo «не умеет JOIN/окна».

Дополнительно измеряются четыре независимых читателя, по пять пакетных
запросов каждый. Подключения, индекс манифеста и warmup вне таймера; результаты
сверяются после. Сохраняются все 20 задержек/повтор, walltime и запросов/с.
Эмпирический p95 при таком размере выборки не является SLA или пределом
производительности. Python/GIL и обработка JSON входят в стоимость клиента S3.

Операции записи/DDL выполняются по одному разу в каждом повторе:

- Полная копия runs: CTAS, `$out`, серверные CopyObject по каждому S3-чанку.
  Копирование индексов отличается; содержимое полной копии сверяется отдельно.
- Переименование этой копии в той же схеме/БД. В S3 это copy+delete
  только что созданного тестового префикса; атомарное переименование каталога
  не предполагается.
- Создание сохранённой месячной сводки: materialized view, `$out`, JSON-объект;
  затем три чтения готового результата. Это одноразовые тестовые таблицы,
  не витрины ЛР3.
- Добавление nullable столбца в PG; в Mongo поля добавляются без такого DDL.
  Изменение поля 1000 существующих ранов отдельно от изменения схемы.
- INSERT 100 явных `benchmark-new:*` копий реальных строк, проверка содержания,
  затем удаление только этих 100 тестовых записей. Это не новые данные источника.
  В S3 изменение/удаление публикует новый манифест, прежние чанки остаются;
  сравнивается выбранный способ работы с историей, не одинаковое освобождение диска.

Для S3 записываются GET/PUT/COPY/DELETE и байты тел. Для PG/Mongo объём WAL,
journal и сетевой протокол не измеряются — нули в S3-специфичных колонках
не означают отсутствия их I/O. copied_bytes — логическая сумма размеров целей
серверного CopyObject, а не объём передачи клиенту или занятое место: сервис
может переиспользовать блоки. Дополнительный readonly alias записывает только
манифест с ссылками на прежние immutable-чанки; это отдельный сценарий снимка
для чтения, не копия независимо изменяемой таблицы. Пространства опыта сохраняются. Счётчики
production PG/Mongo, inventory S3 и бюджеты HTTP до/после должны совпасть;
это контроль отсутствия вмешательства, не полный повторный аудит всего ODS.

Отдельные маленькие probe-таблицы/объекты проверяют PK, FK, CHECK/валидатор,
откат нескольких записей, частичную запись без транзакции и preconditions
PutObject. Mongo остаётся standalone; инфраструктуру ради теста не меняем.
Ограничение транзакций для такого развёртывания указано в
[MongoDB production considerations](https://www.mongodb.com/docs/v8.0/core/transactions-production-consideration/).
Результат конкретного Garage нельзя переносить на Amazon S3 или другие версии.

## PostgreSQL: способ массовой записи

После основного опыта тот же input используется в трёх новых парах `test_wl_*`:
пакетный INSERT executemany против COPY; PK создаются до измерения. Затем
COPY → staging → INSERT ON CONFLICT DO NOTHING проверяет повтор без новых
строк. Каждая загрузка подтверждается commit; полная сверка содержимого после
таймера и не входит в эти времена. Эти числа нельзя напрямую сопоставлять
с прежним временем ODS load, включавшим полную сверку внутри таймера.
Интерфейс COPY — официальный [psycopg Cursor.copy/write_row](https://www.psycopg.org/psycopg3/docs/basic/copy.html).

```powershell
docker compose exec -T scheduler python -u -m speedrun_etl.storage_workloads --pg-bulk-input /opt/airflow/state/benchmarks/workloads_TIMESTAMP/input_100000
```

После переноса только CSV/JSON evidence в отдельную папку отчёта:

```powershell
python reports/lab1/plot_workloads.py reports/lab1/storage_workloads_20261028
```

Для четвёртого графика положить результаты COPY в подпапку pg_bulk. Полные
input SQLite и исходные ответы в Git не передаются. Практические рекомендации
и измеренные числа — в актуальном разделе REPORT.md.
