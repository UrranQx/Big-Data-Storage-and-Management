## Ограничения и известные свойства

Текущие скрипты — только исследовательские прототипы в `archive/research/`.
Рабочих DAG, загрузчиков в выбранные три сервиса и готовой инфраструктуры нет.
Существующие unit-тесты не доказывают готовность универсального ETL.
При этом не переписывай проверенные функции ради нового устройства проекта:
перенос и минимальная адаптация полезного кода предпочтительнее ненужной разработки.

`DATA_MODEL.md` и `DAGs.md` — неутверждённые черновики. Предложи минимальную
конкретную ODS-модель и согласуй её со мной до реализации. Не переноси всю
DDS ER-модель в ЛР1. Тройка БД ещё не утверждена: сравни разумные варианты,
включая PostgreSQL + ClickHouse + MinIO и PostgreSQL + MongoDB + MinIO.
Сделай рекомендацию с учётом ресурсов машины и сырых вложенных JSON, но не
считай прежние рекомендации уже принятым решением. Если предлагаешь S3-сервис,
учти, что объектное хранилище прямо допускается заданием.

Данные: каталог игр; категории/переменные/платформы выбранных игр; все доступные
full-game раны new/verified/rejected, включая obsolete; все участники этих ранов,
не только лидеры. Сохраняем сырые ответы, имена и ID, все доступные таймеры,
даты, происхождение, параметры/время запросов и диагностику покрытия.
Level runs и отдельные Category Extensions исключены из основной области ранов.
Orphaned не удаляем из ODS; его аналитическое исключение не означает потерю raw.
Участник, submitter и moderator — разные роли. API v2 — основной, v1-аудит
опционален; ограничение смещения v1 и пропуски отдельных записей v2 известны.
Не обещай гарантированную полноту сайта и не считай stats эталоном без проверки.

Общий бюджет — 20 запросов/мин для всех процессов и DAG вместе, с 429 и
Retry-After. Внутрипроцессный lock прототипа не решает общую координацию Airflow.
Подбери простейший рабочий механизм общего ограничения под выбранный режим
выполнения: не добавляй отдельный сервис, если проблему решает меньшая схема.
XCom — только небольшие метаданные и ссылки, не большие ответы API.

Сохранность истории нужна для разных будущих исследований ЛР2–ЛР3, не только
PB/WR. Сохраняй полные исходные поля в согласованной области, а не только уже
выбранные аналитические признаки. Прочитай раздел «История без дублей»
в `SOURCE_CONTRACT.md` и предложи конкретный способ его выполнить:
идентичность сущности, исходное содержимое, наблюдение и запуск — разные вещи.
Retry не создаёт дублей; новая проверка неизменного состояния не требует
ещё одной полной копии. Изменения сохраняются без затирания предыдущего;
возврат A → B → A не должен теряться из-за дедупликации hash. Даты источника
отдельны от времени обнаружения. Это захват истории в ODS ЛР1, а не реализация
SCD, исторического лидерборда или всей DDS сейчас. Raw + manifest — вариант,
а не заранее утверждённое решение. Не обещай точную историю до начала наблюдений.

Для профильного DAG ещё нужно проверить доступность необходимых полей.
Сначала проверь, достаточно ли профилей, встроенных в уже получаемые ответы.
Отдельный endpoint и запрос на каждого участника не являются обязательными.
При необходимости дополнительных полей укажи ограниченную проверку нескольких ID.
Недоступные/гостевые профили и отсутствие страны не должны ломать загрузку.
Не запускай эту сетевую проверку автоматически на текущем этапе планирования.

Цель пользователя — собирать заново глобальный каталог и максимально доступные
данные по всем играм в согласованной области через итоговый ETL, а не завершить
работу на одной игре. Предложи небольшой первый e2e, затем одну полную игру
для проверки, затем управляемый обход каталога. Portal — кандидат только для
проверки. Не подменяй глобальную цель минимальным демонстрационным набором.
Старые выгрузки/профили не использовать вместо нового сбора. Пользователь
рассматривает их удаление, но перечень удаления ещё не утверждён.
Повторный запуск не дублирует тот же пакет, свежий снимок не подменяется кэшем.
Частичные сбои трёх загрузчиков, дрейф пагинации и неполное покрытие должны быть
наблюдаемы. Оцени общее время, число запросов и объём хранения для глобального
сбора, предложи контрольные точки, продолжение и обновление без повторного
полного обхода при каждом запуске. Пока объём неизвестен, дай измеримый способ
оценки, а не придуманную длительность. Повтор раздела допустим, полный перезапуск
всего каталога после каждого сбоя — нет. Выбирай последовательный сбор,
если он достаточен; не вводи
распределённый limiter или отдельный сервис ради ненужной параллельности.
Для ODS достаточно raw + небольшой manifest, а не всех служебных таблиц,
перечисленных в черновике. Не разрабатывай универсальный ETL-фреймворк.

Не выполнять сейчас ЛР2/ЛР3: DDS, SCD, расчёт PB/WR, отдельный DDS DQ DAG,
аналитические витрины, Superset, OpenMetadata. Не создавать пользовательский
сайт: он вообще не требуется заданием. Twitch/YouTube, эмбеддинги, ML,
рекомендации и уведомления — необязательные идеи, не текущий объём.
Структура репозитория должна позволять позже добавить ЛР2–ЛР3 без дублирования
клиента и без переписывания всего проекта. Не вводи лишние сервисы и абстракции.
Защиту темы и таблицу занятых источников не обсуждаем — этот вопрос закрыт.

Секрет `SPEEDRUNCOM_API_KEY` ранее использовался через переменную окружения.
Не выводи значение, не записывай в файлы и не передавай в API v2.
`data/` и локальный ZIP не включать в Git, Docker build context и отчётные коммиты.
Не удалять существующие данные. Не создавать remote, не публиковать и не push.

## Что получить в результате планирования

1. Краткий аудит: что реально есть, что отсутствует, какие риски ещё не проверены.
   Проверь Docker/Compose/Engine, Python, ресурсы и доступность нужных портов
   без запуска/остановки чужих сервисов. Если сведения недоступны, так и укажи.
2. Конкретную рекомендацию по трём хранилищам, версиям и минимальной топологии
   Airflow. Проверь совместимость и инструкции по официальным источникам.
   Отдели техническую metadata DB Airflow от трёх целевых сервисов ODS;
   совместное использование одного PostgreSQL допустимо, если явно разделены
   базы/пользователи и измерения не смешивают служебные данные с данными ODS.
3. Минимальную ODS-схему для каждого хранилища: ключи, raw и manifest,
   единица снимка, сохранение ID/имён, повторная загрузка, ошибки и покрытие.
   Объясни сохранение изменившихся исходных состояний без дублей payload,
   свежие проверки и retries, сроки хранения технических записей. Предложи
   проверки: повтор без изменений, изменение и возврат старого состояния,
   retry после частичной загрузки. Отдельные нормализованные справочники и таблицы на каждый тип наблюдения
   не обязательны в ЛР1, если информация сохраняется в исходных ответах.
4. Схемы трёх DAG: задачи, входы/выходы, зависимости, лимиты, retries,
   артефакты, fan-out загрузки и критерий успешного завершения.
5. Небольшой метод сравнения: одинаковые данные, время загрузки, занимаемый
   объём и простое чтение. Дополнительные критерии — только если полезны.
   Для S3 не добавляй внешний SQL-движок: ограничения запросов отрази в выводах.
   Определи объём, несколько повторов, условия измерения и простую итоговую
   таблицу/график. Отдельная платформа нагрузочного тестирования не нужна.
6. Поэтапный план реализации с конкретными файлами и проверяемыми критериями:
   инфраструктура → небольшой e2e → одна полная игра → обход каталога → повторы/сбои
   → сравнение → отчёт/демонстрация. Не заявляй успешные замеры до выполнения.
7. Матрицу «требование ЛР1 → артефакт → проверка/демонстрация» и явный список
   исключённого объёма. GitHub нужен по заданию, но публикация будет отдельным
   действием после появления remote и моего запроса.
8. В конце — минимальный набор вопросов для утверждения: стек, ODS и область
   сбора. В каждом предложи рекомендуемый вариант, чтобы мне не пришлось
   проектировать решение с нуля. Дождись моего утверждения перед реализацией.
