## 1. Дизайн схемы DDS

В PostgreSQL спроектирована схема `speedrun_3nf` из 30 таблиц. Таблицы идентичности сохраняют исходные ID Speedrun.com. Например, `dim_game.game_id` соответствует `entity_v3.games.source_id`. Название игры, её настройки и счётчики вынесены в `dim_game_version`. Аналогично отдельно хранятся игроки и версии профилей, раны и версии их состояния. У наблюдаемых версий есть внутренние ключи и поля `valid_from` и `valid_to` для хранения истории.

Категории, платформы и значения переменных вынесены в связанные таблицы. Вложенные списки, например платформы игры и участники рана, раскладываются по строкам. Поле `position` хранит индекс элемента в исходном списке и позволяет восстановить его порядок. В истории WR отдельно хранятся условия зачёта, события и раны, входящие в каждое событие. Полные ответы API и исходные наблюдения сохраняются в `entity_v3`. [Схема DDS и её описание](../../docs/design/entity_v3_3nf.md)

## 2. DAG нормализации

После успешного завершения цепочки ODS задача `players` публикует событие Airflow с ID снимков этапов `games_metadata`, `runs`, `wr_history` и `players`. При самостоятельном сборе метаданных событие публикует `games_metadata` со своим ID снимка. Событие запускает `normalize_entity_v3`, а его сенсор проверяет наличие квитанции PostgreSQL ODS для каждого переданного снимка.

Загрузчик извлекает из `entity_v3.checks` наблюдения, относящиеся к этим снимкам, и читает версии по указанным в наблюдениях ключам. По ним он заполняет таблицы `speedrun_3nf`. Данные каждого набора снимков и отметка о его обработке фиксируются одной транзакцией. Если событие доставлено повторно, уже обработанный набор пропускается. Для исторических снимков предусмотрен отдельный запуск по архиву. [DAG нормализации](../../dags/dds/normalize_entity_v3.py) · [Загрузчик DDS](../../src/speedrun_etl/dds.py)

## 3. Проверка качества данных

После успешной записи всех наборов снимков DDS публикует событие для DAG `check_data_quality`. Он выполняет две группы проверок.

- **Сверка объёмов по снимкам.** Для игр, ранов и публичных профилей подсчитываются исходные наблюдения ODS и сопоставляются с версиями DDS по ID сущности и времени наблюдения. Гостевые профили исключаются по тому же правилу, что и при нормализации.
- **Поиск аномалий в DDS.** Проверяются отрицательные счётчики и длительности, неизвестные статусы ранов, время верификации раньше времени подачи и закрытые интервалы версий ранов без даты начала.

Отчёт с объёмами и количеством нарушений записывается в журнал задачи. При расхождении или аномалии задача завершается ошибкой. На временном PostgreSQL проверены корректный набор данных, пропущенная версия и неизвестный статус рана. Связь DAG через событие проверена без запуска рабочего планировщика.

Сверка объёмов WR пока отсутствует. При загрузке `fact_wr_event` получает локальный `event_id`, а связь этого ключа с конкретным наблюдением ODS не сохраняется. Совпадающие по содержимому события из разных снимков поэтому нельзя однозначно отнести к отдельному запуску.
