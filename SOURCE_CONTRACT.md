Актуализация пагинации 2026-10-27: самосогласованное изменение count/pages
при прежнем per больше не обрывает раздел немедленно. Сборщик продолжает
доступные страницы с уточнением границы, сохраняет дрейф/повторы ID между

стабильном count изменение граничных ID по-прежнему допускает один повтор.
Полные исходные ответы и прежние проходы не удаляются, атомарность не обещается.

coverage_retry и продолжает другие игры после подтверждения всех трёх ODS.

не обходят. Без флага сохраняется остановка на partial. Оптимизация playerList
пользователем назначена обязательной следующей работой и пока не завершена.

## Область и подтверждённые свойства

Основная область проекта: публичные раны полной основной игры во всех трёх
статусах, включая прежние результаты. Level runs и отдельные Category Extensions
исключены из основной аналитики. Политика пользователя: v2 — основной источник;
orphaned исключаются из статистики, исходные свидетельства сохраняются.
V1-аудит и его записи хранятся отдельно и не добавляются автоматически в v2-аналитику.

Флаг obsolete и обычный статус независимы. В текущих наборах есть obsolete
verified, rejected и new. Подтверждённых obsolete: Portal 10 713 из 16 620,
Minecraft Java 17 022 из 29 373. Следовательно, текущая выгрузка v2 с obsolete=1
содержит прежние результаты, а не только результаты текущей таблицы рекордов.
Повторяемая локальная проверка: `python inspect_obsolete_history.py`;
количества и примеры: `data/research_20261010/obsolete_evidence.json`.

Документация v1 различает обычные лидерборды с non-obsolete и архив /runs:
- https://github.com/speedruncomorg/api/blob/master/version1/leaderboards.md
- https://github.com/speedruncomorg/api/blob/master/version1/runs.md
- https://github.com/speedruncomorg/api/blob/master/version1/variables.md

V2 — API веб-интерфейса, его параметры и поведение проверяются отдельно;
документация v1 не является спецификацией v2. Наблюдения для нескольких игр
не доказывают полноту публичной базы для всех игр.

## Универсальный алгоритм для каждой игры

1. Получить и сохранить метаданные игры, всех доступных категорий (включая
   архивные), переменных, значений, платформ и правил. Сохранить версию снимка.
2. Разделить категории по типу full-game/per-level и состоянию archived.
   Архивность, orphaned, отсутствие игроков и составной результат — отдельные
   признаки. Не выводить один автоматически из другого.
3. Для каждой full-game категории запросить v2 отдельно по verified/rejected/new,
   с включением obsolete, без ограничения видео/подкатегории в основном архиве.
   Проверять фактическое соблюдение параметров, а не только успешный HTTP.
4. Проверить каждую страницу, количество и уникальность ID, принадлежность
   игре/категории/статусу, отсутствие IL. ID определяет ран; player_id не является
   ключом дедупликации. Проверять изменения состава при смещении страниц:
   одинаковое count не исключает изменения ID между запросами.
5. Проверять возможности источника для игры: доступность архивных списков,
   страницы за 10 000, порядок и фильтры. Пустой архивный лидерборд означает
   пустой ответ данного endpoint, а не отсутствие исторических ранов.
6. При включённом v1-аудите сопоставлять ID, а не только суммы. Общий список
   /runs игры может содержать архивные категории, недоступные через фильтр category.
   Сортировка только по категории дала повторы между страницами; её нельзя
   считать доказательством полноты уникальных ID. Разбиения по пользователю,
   проверяющему и другим подтверждённым фильтрам должны иметь проверенный охват.
7. Записать coverage по разделам. `all_v2_partitions_checked` означает проверку
   всех выбранных публичных списков v2. Это не `all_runs_on_site_collected`.
   Статусы покрытия: verified_public_partitions / partial / unavailable /
   not_checked. Завершение DAG и полнота источника — разные свойства.
8. Сохранить stats до/после с временем наблюдения. Совпадение суммы со stats
   не доказывает формулу или участие конкретного ID. Несовпадение создаёт
   диагностический результат, а не автоматическое удаление или добавление ранов.

Правила исключения применяются в аналитических представлениях. Всё полученное
сохраняется в ODS с признаками и происхождением. Составные категории вроде
Minecraft Combined распознаются по правилам и доказательствам; универсального
API-признака «агрегат нескольких PB» пока не подтверждено. Для неизвестных
категорий сохранять classification=unknown, а не угадывать по названию.

## Возможные сущности ODS для ЛР1

Это логические понятия, не обязательный список отдельных таблиц.
Для небольшой реализации достаточно исходных ответов и манифеста снимка,
сохраняющих эти сведения без сложной схемы наблюдений.

### Уточнение перед реализацией: история без дублей

Цель ЛР1 — сохранить исходные сведения для разных будущих исследований,
а не только для PB/WR. В согласованной области сохранять полные публичные
payload, включая пока не используемые поля и вложенные структуры. Не заменять
их выборкой только тех атрибутов, которые уже нужны конкретному графику.
Это относится к играм, категориям, правилам, переменным/значениям, платформам,
ранам, участникам, профилям и статистике, где она доступна.

Различать сущность источника, полученное содержимое, наблюдение и запуск ETL:

- Повтор обработки того же пакета или retry не создаёт дубликат сущности,
  содержимого или того же наблюдения. Ключи идемпотентности выбрать в плане.
- Новая проверка неизменившейся сущности может добавить небольшую запись
  наблюдения или обновить отметку проверки, без новой полной копии payload.
  Нужную детализацию проверок и срок хранения технических журналов согласовать.
- При изменении сохранять прежнее и новое исходное состояние с происхождением
  и временем наблюдения. Простое затирание текущей строки теряет историю.
- Возврат состояния A после B должен оставлять последовательность A → B → A.
  Дедупликация содержимого по hash допустима, но не должна склеить эти периоды.
- Изменение порядка строк на странице или соседнего объекта не означает
  изменение всех сущностей страницы. Контекст API, параметры и версия способа
  сравнения должны позволять объяснить обнаруженное изменение.
- Даты событий источника сохранять отдельно от requested_at/fetched_at/observed_at;
  исходные NULL и точность не подменять предположениями. Смена флага между
  проверками задаёт интервал обнаружения, а не точную дату события.
- Ошибка запроса, неполная страница или отсутствие записи не являются
  доказательством удаления и не должны автоматически закрывать её историю.

Это требования к сохранности информации, **не утверждённая физическая схема**.
Raw + manifest — возможное представление, не обязательный файловый стандарт
и не разрешение создавать полную копию сайта при каждом запуске. Нужен план
сохранения исходных состояний и наблюдений в выбранных трёх сервисах; конкретные
ключи, дедупликацию, хранение страниц и очистку временных артефактов утвердить
с пользователем. Не удалять единственный источник полей до их надёжного сохранения.

В ЛР1 реализуется захват исходных изменений без потери истории. В ЛР2 —
нормализация, SCD и вычисляемые интервалы/признаки; в ЛР3 — витрины и визуализации.
Точная история сайта до начала наблюдений не гарантируется. Это ограничение
отражать для любых будущих временных исследований, не только для рекордов.

| Сущность | Содержимое |
|---|---|
| ingestion_batch | snapshot_id, начало/конец, версия сборщика и политики, состояние |
| source_response | endpoint/API, параметры, requested_at/fetched_at, HTTP, payload, hash |
| entity_observation | entity_type, entity_id, snapshot_id, observed_at, payload, hash |
| coverage_partition | игра, категория, статус, параметры, expected/received/unique, ошибки |
| site_stats_snapshot | game_id, observed_at, исходные счётчики |
| run_observation | run_id, наблюдаемые атрибуты, источник, контекст запроса, связь с raw |

Сохранять status, obsolete, orphaned, issues, участников, автора подачи,
времена всех таймеров, даты выполнения/подачи/решения, переменные и их значения.
Секреты и заголовки авторизации не сохранять. Ошибки и HTTP 404 записывать
как наблюдения; один 404 или отсутствие на странице не означает удаление.
Неизвестные значения переменных сохранять в raw и отмечать в DQ.

Разные ответы могут отражать разные контексты лидерборда. Исходные obsolete
и place сохранять с параметрами запроса; конфликты не затирать незаметно.
Каноническая сущность run имеет один ID; наблюдений одного ID может быть много.

## Четыре разных понятия актуальности

| Понятие | Смысл |
|---|---|
| source_obsolete | Признак источника в данном снимке/контексте |
| PB | Лучший допустимый результат игрока/команды в определённом зачёте |
| WR | Лучший допустимый результат среди всех участников зачёта |
| observed_state | Состояние записи, обнаруженное нашей системой |

Non-obsolete не означает WR. Obsolete не означает «когда-то был WR» и не
гарантирует, что ран когда-то был PB: более медленная попытка могла никогда
не становиться лучшим результатом. Не определять PB/WR только по source_obsolete.

## Зачёт и вычисление истории для DDS — ЛР2

Зачёт (`leaderboard_scope`) определяется версией правил: game, category,
релевантные переменные, выбранный таймер, направление сравнения и фильтры.
Платформу/регион добавлять в ключ только если этот зачёт их разделяет.
Не объединять весь Any% в один WR и не разделять его по всем атрибутам подряд.
Метаданные об obsoletes/isObsoleting и is-subcategory/isSubcategory сохранять:
они имеют разный смысл. Правила Co-op и playerMatchMode требуют собственной
проверки; нельзя автоматически сравнивать личный и командный результат.

Таблица истории: `record_period(scope_id, record_kind, holder_id, run_id,
valid_from, valid_to, time_basis, reconstruction_method, confidence,
rules_version, calculated_at, evidence_snapshot_id)`.

- record_kind: PB или WR; holder_id означает игрока или команду.
- Интервалы полуоткрытые [valid_from, valid_to). valid_to=NULL означает, что
  замена пока не известна в рамках выбранной модели; в отображении можно
  подставлять максимальную дату. Не утверждать, что результат останется вечным.
- Один run_id может иметь несколько интервалов: после отмены нового рекорда
  прежний может снова стать лучшим. Поэтому пара дат не является единственными
  атрибутами строки runs.
- Перебирать события внутри зачёта по выбранному времени, обновлять минимум
  или максимум согласно правилам. Событие улучшения завершает предыдущий период.
  Более медленные попытки не открывают период PB/WR.
- Все исторические verified-кандидаты рассматриваются, включая obsolete сегодня.
  Сегодняшний non-obsolete фильтр нельзя применять к реконструкции всей истории.
- Равные результаты могут иметь нескольких держателей. Правило обработки ничьих
  хранить явно; нельзя произвольно назначить одного владельца или время смены.
- Использовать точные числовые длительности/единицы и точность правил, а не
  отображаемые округлённые строки. IGT, RTA и время без загрузок не смешивать.
- Нет даты или неизвестен момент решения — сохранять неопределённость;
  отсутствующие timestamps/таймеры не выдумывать. Точность даты не гарантируется
  одним лишь наличием ISO timestamp.

## Два времени, которые нельзя смешивать

1. Реконструкция по performed_at отвечает «какой результат был лучшим по дате
   выполнения среди известных нам допустимых ранов». Это ретроспектива,
   использующая сведения, полученные позже; не точная история публикации на сайте.
2. История по verified_at отвечает иной модели. Поле текущей карточки может быть
   неполным или относиться к повторному решению, а прежние решения отсутствовать.
   Её нельзя объявлять достоверной полной историей фактического лидерборда.

В ЛР1 сохранять исходные наблюдения. В ЛР2 из них отдельно формировать
наблюдаемую историю: `run_state_version(run_id,
observed_from, observed_to, status, payload_hash, snapshot_id, ...)`.
Если в t1 запись new, а в t2 verified, фактический переход произошёл после
последнего наблюдения new и не позже первого verified. Точность наблюдения
равна расписанию сбора. observed_from не подменяет source_event_at.

Сохранять публичную историю WR источника как самостоятельные исходные ответы
для каждого проверенного зачёта (ЛР1). Собственную реконструкцию выполнять
в ЛР2, аналитическое сопоставление — в ЛР3.
История положения игрока на всех местах отличается от истории его PB:
место меняется при улучшении других игроков даже без нового рана этого игрока.

## Обновления

В ЛР1: новый snapshot_id и неизменяемые raw-ответы; наблюдения не
перезаписываются. При неизменном payload всё равно фиксировать успешное
повторное наблюдение. В ЛР2: версии сущностей и upsert по ID для текущего
состояния DDS, с сохранением истории изменений.

Новые подачи, pending, изменения уже подтверждённых/отклонённых ранов,
архивирование категорий и изменения правил — разные потоки обновлений.
Недавние окна с перекрытием дополнять регулярной полной сверкой выбранных игр:
старый ран может поменяться спустя годы. Date-фильтры v2 пока нельзя считать
надёжными: проверенные dateFrom/dateTo были проигнорированы источником.
Постоянный кэш нынешнего сборщика служит возобновлению снимка, не обновлениям.

Исчезновение из списка — событие доступности. Повторять проверку карточки и
различать unavailable, excluded_by_source, archived, orphaned и unknown.
В ЛР2 изменение исходных правил требует пересчёта соответствующих derived-историй,
с сохранением предыдущей версии методики.

## Как перенести в ЛР1

Утверждённые сервисы для сравнения: PostgreSQL (raw JSONB и SQL), MongoDB
(документы ответов/наблюдений), Garage (S3 JSON-объекты). Данные одного
снимка извлекаются один раз и загружаются в три хранилища; повторный независимый
сбор для каждого хранилища сделал бы сравнение некорректным и увеличил нагрузку API.

Три логических DAG: games_metadata, runs, players; stats/WR входят в runs.
Runs ждёт нужного снимка метаданных; players использует всех полученных
участников, а не только текущих рекордсменов. Все DAG используют общий
ограничитель 20 запросов/мин на весь проект, а не по 20 на каждый task.
Retry-After/429, повторный запуск, уникальность загрузок, исходные ответы и
coverage обязательны. ЛР1 собирает доказательства и историю наблюдений;
нормализованные PB/WR-интервалы формируются в DDS ЛР2, витрины — в ЛР3.

Сравнение сервисов: время загрузки одинакового снимка, объём хранения,
извлечение рана по ID, выборки по игре/категории/статусу, обновление наблюдений,
удобство истории и подключения аналитики. Для Garage фильтрацию выполнять
клиентом, без добавления SQL-движка.
Основной аналитический DDS удобно строить в PostgreSQL; выбор обосновать замерами.

До реализации зафиксированы границы полноты, правила сохранения и определения
истории. Дополнительные особенности игр регистрируются в capability/coverage,
не маскируются под универсально успешную выгрузку.
